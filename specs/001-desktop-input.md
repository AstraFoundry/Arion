# 001 Desktop input

## Requirements

- DSK-01: Dictation MUST select its delivery route at session start from the actual OS input source: the selected Arion input method uses its owned client; other sources use external-editor delivery. The route stays fixed for that session. Settings MUST NOT expose input-mode or delivery-transport controls. Legacy stored `mode` values are ignored and omitted on the next preference save. Losing an owned IME client cancels that session and invalidates its generation; it MUST NOT cancel external-editor dictation or trigger a second delivery route.
- DSK-02: Shortcut mode is activated globally by a single dictation key observed through a tested native key-down/key-up adapter (macOS listen-only event tap with Input Monitoring consent; Windows low-level keyboard hook); MyGo activation callbacks alone are insufficient. There is no separate accelerator toggle and no "off" choice: the key defaults to Right Option on macOS and Right Alt on Windows, and a stored key the platform cannot observe is repaired to that default. Holding past the threshold (300 ms) stops on release; a shorter tap keeps dictating until the next press; another key during a hold that started the session cancels it. macOS readiness requires Input Monitoring consent and an enabled tap, rather than merely a non-null tap object; granting missing consent restarts the selected listener, and revocation cancels capture and retires it. Listener replacement rejects queued events from the retired listener. A key that cannot listen MUST report why with a way to fix it; onboarding does not continue until the key listens. The in-app dictation button, tray menu and the macOS input menu's Voice input item ([IME-06](007-ime-ranking.md)) remain local toggles.
- DSK-03: The user MUST see recording, processing, candidate preview, permission failure and insertion failure states, including above another application's native macOS fullscreen Space without activating Arion or taking the editor's focus. Permission requests occur only for enabled capabilities.
- DSK-04: Capture starts only after microphone consent and ends on stop, cancellation, OS suspend or device removal. Quit releases microphone, hotkeys and owned IME composition.
- DSK-05: A target snapshot MUST include stable platform identity, editor capability, selection/range ownership, generation and sensitive-field status. The portable token is opaque; native handles stay in the adapter.
- DSK-06: On macOS, shortcut delivery MUST use system paste with per-transaction clipboard snapshots and ownership-checked restoration; system-IME delivery retains the owned IMK client. Posted paste MUST remain `unknown` without a host acknowledgement; restoration failure MUST retain that outcome and warn before user retry. Cancellation MUST reach the adapter, prevent pre-post writes and suppress late completion. Shortcut drafts stay in Arion's preview. Commit MUST revalidate target and selection and insert once. A focus change, uncertain write result or unsupported target MUST require user action rather than a second automatic attempt.
- DSK-07: IME mode MUST follow the host's composition/candidate lifecycle and release all owned ranges on cancellation/deactivation. See [007](007-ime-ranking.md).
- DSK-08: Block context extraction and memory learning from secure/password fields. If the adapter cannot establish field safety, it cannot read its content.
- DSK-09: Model missing/unsupported hardware/permission denied MUST be actionable explicit errors; never silently use cloud inference.
- DSK-10: The interface MUST offer English (default) and Simplified Chinese in settings and onboarding, persist the choice, and update existing windows without restarting recognition or altering user content. UI language MUST remain independent of recognition/model selection.
- DSK-11: On macOS, a packaged Arion asking for Accessibility or Input Monitoring MUST open that privacy pane in System Settings with a nonactivating guide under its window that offers Arion's app to drag into the list. The guide follows the window, shows only while System Settings is frontmost, and closes on consent (returning focus to the Arion window that asked), on its close button, or when System Settings quits. Microphone keeps its initial system prompt; its settings entry adds a compact switch guide. Screen Recording keeps its native request and adds the same compact guide while settings authorization remains missing. These guides contain one instruction, offer no drag payload, and close only after their own permission is observed granted. An unbundled build keeps the native platform actions. The guide never changes consent itself. Keyboard input-source setup reuses its window-following shell with adding/allowing instructions instead of a draggable app tile; it returns to Arion on observed enablement. The onboarding input-method page separately waits for current selection before Continue and offers Set up later.
- DSK-12: Settings › Microphone MUST offer a stepped software input gain from −6 dB to +12 dB in 3 dB steps, 0 dB by default, labeling each step with the speaking distance it suits (15 cm at −6 dB to 120 cm at +12 dB; speech level falls 6 dB per doubling of distance from a 30 cm reference). Gain scales only Arion's capture, clipping at full scale, applies to the live meter and to dictation without reopening the device, persists, and never changes the OS input volume.

- DSK-13: Settings › About MUST offer a user-triggered local diagnostic ZIP export through the native save dialog, with progress and explicit failure feedback in both interface languages. Cancellation creates no export; success reveals the file for inspection. No automatic upload is permitted.
- DSK-14: First launch MUST show onboarding. Completing onboarding MUST open and focus Settings so the app remains visible, and SHOULD show a nonactivating card beside the tray icon pointing out where Arion stays until it is dismissed or the icon is used; subsequent launches with completed onboarding remain resident in the menu bar or system tray.
- DSK-15: A newer eligible update MUST remain accessible through the tray and About. After input and managed work become idle, a nonactivating reminder offers View update, Later and Dismiss. Submission, a 24-hour Later deadline and dismissal are persisted by channel/version/phase; submission is not proof of OS display. Reminders MUST NOT contain input content, steal focus or submit during active input. System notifications are opt-in; requesting authorization is a separate explicit action. Disabled OS notifications retain the in-app reminder surface.
- DSK-16: Automatic update downloading defaults off and persists independently of automatic checks. Both switches must be on for automatic checks to prepare an update; manual checking does not install automatically. Preparation verifies the existing signed artifact without replacing the installation. Disabling automatic downloading cancels its preparation and discards its unapplied stage. Application replacement occurs only in an explicit guarded restart, after session/commit teardown, managed writes, resource loads and IME maintenance are idle, and while new input is excluded. An active legacy IME client conservatively delays restart. The independent keyboard host is not terminated by the main-app update. No automatic restart is enabled.
- DSK-17: Prepared updates MUST survive restart through revalidated staging records. Late results from a canceled operation or old channel cannot change state. Failed replacement with successful rollback requires fresh preparation; interrupted replacement or failed rollback preserves its journal/backups and reports repair required without retrying or accepting new input. A completed installation receipt is acknowledged only after clearing its persisted staging handle. A vetoed relaunch keeps input paused and exposes Retry restart, because the old process must not load newly replaced resources.

- DSK-18: Account-targeted product notifications MUST be a separate opt-in, off for new/migrated profiles, available with the standard center and explicit OS authorization. While running, authenticated product-scoped polling discovers newest notices and bounded next-launch catchup without per-input queries or focus activation. Sign-out/account switch/disable invalidates stale work. Title/body and at most two dismiss/safe HTTPS buttons MUST be bounded and validated. Cold activations resolve persisted current-account metadata; the backend MUST authorize the current receipt before any URL opens. Successful OS submission is `received`, never proof of display/read. No immediate reception while fully quit is promised ([ADR 026](../docs/decisions/026-account-product-notifications.md)).

| DSK-A10 | Choose a hold key → hold, speak, release → final commit exactly once; tap → dictation continues until the next press; hold key + another key → session cancelled, nothing inserted; missing Input Monitoring on macOS → explicit status and a grant action in settings and onboarding; onboarding waits until the key listens |

Compatibility must be recorded per app/version/input mode on both OSes: native editor, browser editable field, Electron editor, office document, terminal, noneditable field and elevated Windows app. These are test categories, not established support claims. Never auto-send Enter or execute a terminal command.
