# 009 Contextual local rewriting

## Status and scope

This spec defines an optional local LLM stage and its evaluation boundary. The production desktop implements the [rewriting pipeline](#live-rewriting-pipeline) of [ADR 011](../docs/decisions/011-live-local-rewriting.md), [ADR 023](../docs/decisions/023-final-only-polishing.md) and [ADR 025](../docs/decisions/025-windows-local-polishing.md) on macOS (Apple silicon) and Windows x64: recognition may close a segment during speech, and one validated rewrite is inserted after the dictation key is released, in an isolated GGUF pipe worker and private native child. It also implements [scene selection](#scene-selection) from the focused field, web site and app. macOS context capture supplies the staged selector; actual Windows context collection and the strict [rewrite evaluator](../docs/research/rewrite-evaluation.md) integration remain separate acceptance scopes. Competitor artifact findings do not establish that Arion or a competitor executes this pipeline.

Rewriting is separate from acoustic recognition, conservative correction and Laya candidate ranking. A ranker permutes existing producer candidates; a rewriter can generate a new text proposal. Baseline dictation remains available with rewriting disabled. macOS shortcut, Windows shortcut and optional IMK/TSF hosts share the portable request/result contract; host integration must be verified on the actual OS.

## Product pipeline

1. Obtain revisioned ASR text and conservative correction. Preserve their original text independently of any rewrite.
2. Capture a bounded context snapshot and approved memory under [rewrite context](#rewrite-context). Select a scenario from explicit user choice and permitted application hints. Unknown/secure targets deny context acquisition before reading their values. Clipboard remains unread; other sources need their own switch.
3. Build a versioned prompt with trusted rewrite instructions separated from untrusted transcript/context/memory. Pin template, tokenizer, checkpoint, GGUF artifact, conversion, quantization and execution provider. User text may describe commands; it never grants tool execution, networking or target writes.
4. Run bounded non-thinking generation locally, once, after the user releases the dictation key. Keep token streams separate from recognized drafts and owned IME composition. The session does not send a rewrite while capture continues, and a model result cannot replace recognized text before release.
5. In polishing mode, run source-relative spelling selection followed by scene formatting, using the adopted [product configuration](../docs/operations/local-rewrite.md). Only protocol completeness, UTF-8, output budget and control markup gate delivery; semantic overlap proxies do not reject output. Preserving facts, negation, modality and intent remains the model instruction and review objective, not a string-based guarantee. Verbatim mode bypasses rewriting.
6. Deliver the validated proposal automatically ([ADR 011](../docs/decisions/011-live-local-rewriting.md)) and keep the recognized original available to copy. A generated instruction, reasoning block, skill invocation or model refusal is never inserted as ordinary dictated text. Rejection, timeout, missing model and unsupported runtime are explicit organization outcomes recorded with the result. They retain the completed local speech-cleanup result; raw recognition and rule-corrected source remain separate.
7. Commit only through the existing once-only target capability after source identity, focus and mode checks. Source revision, cancellation, focus change or mode switch invalidates the proposal and owned composition. A late token, preview or callback cannot write to a target.

## Live rewriting pipeline

- LRW-01: While the user is speaking, closed recognizer segments stay recognized text. The open segment is displayed after them. No closed segment is sent to the rewrite model during speech, and no polished preview is shown. Recognition may still close a segment after quiet or the segment limit ([ADR 023](../docs/decisions/023-final-only-polishing.md)).
- LRW-02: A segment's audio is cut inside the pause that closed it, not at the moment the endpoint was reported. Per-segment finalization is a bundle choice; without it the finalizer decodes the whole utterance once after stop.
- LRW-03: A model result is not displayed during capture. It cannot replace recognized text before the user releases the dictation key. A rewrite failure never ends the session by itself.
- LRW-04: Release runs one final rewrite of the full recognized text. That request's text is the recognized source, not a polished replacement. Cancellation, mode change or a new session discards the final proposal; the worker releases the session's KV state when the session ends.
- LRW-05: Every proposal passes `domain.ValidateRewriteDelivery` on the raw model text before punctuation conversion, display, insertion, or preview reuse: nonempty valid UTF-8, complete output and no chat/prompt control markup, including a copied `<source>` tag. A conversion that leaves only whitespace is rejected and is not cached. Length/overlap, numbers, negation, uncertainty and OCR-copying proxies no longer veto output. The user accepted the baseline's known development errors; this does not certify every output or minimum-hardware acceptance. Historical `ValidateRewrite` remains for report replay only. The inserted text uses the punctuation mode. Omit and spaces post-edit that text. Smart and full keep the model's punctuation. The session does not show a polished preview during speech.
- LRW-06: The isolated worker owns a pinned offline GGUF child over a private Unix socket on macOS and Windows, never loads the speech runtime, and keeps context out of the final formatter. Windows socket storage uses a protected current-user DACL, its hidden workers are owned by a kill-on-close Job Object, and CPU backend dispatch uses only packaged dependencies. Template/tokenization uses the artifact's embedded Jinja with thinking disabled. Preparation renders/tokenizes without generation or KV precomputation. Session end erases the native slot; no prompt cache is saved to disk.
- LRW-07: Model weights download only after an explicit Download or Retry action, with the resource size shown before confirmation, as SHA-256-pinned files published atomically; selecting the local engine or enabling polishing alone does not authorize a download. Startup loads verified installed weights only; missing or cancelled downloads await another explicit action. Cancellation or switching off/to cloud invalidates queued download work. Download confirmation, progress, cancellation and retry belong to the local option, before the cloud option. The selected local header stays compact with a trailing primary Download action until confirmation. During provisioning, Cancel download occupies the same trailing slot instead of a separate row below progress. Provisioning reveals its progress panel through an interruptible eased height/opacity transition, respecting reduced motion. The local trailing check indicates a ready worker only; completion collapses the panel. Onboarding permits continuing with local polishing after its confirmed download starts, or while its installed worker is loading/ready; it waits while confirmation or retry is required. The runtime ships signed inside the app. Platforms without a pinned runtime report the capability as unsupported.
- LRW-08: Polishing enabled by the user stays enabled while its worker is loading or unavailable. If no worker can serve the final request, record `unavailable` and deliver the completed local cleanup; never label that session as polishing disabled.

- LRW-09: With polishing enabled, `domain.CleanSpeech` produces versioned deletion spans in the unchanged rule-corrected source before organization. Spans have UTF-8 byte boundaries, known kinds, increasing nonoverlapping ranges and cannot intersect quoted/code text. The local producer (`speech-spans-v2`) handles declared hesitation/scaffolding, limited stutters, and repairs with a repeated frame or matching typed value. After an explicit Chinese repair cue, an optional copula is accepted only when the replacement occupies the entire clause and has the same typed unit; negation, uncertainty, quoted text and unrelated predicates remain protected. Ambiguous expressions remain model input; a cue alone is insufficient. Cleanup adds no content, preserves all-padding input, and is retained if organization fails. Disabled polishing and verbatim mode do not run this stage. Span production is Arion's implementation, not a recovered competitor model.
- LRW-10: In polishing mode, the formatter normalizes unambiguous spoken quantities to Arabic digits, including decimal points, sign, percentages and every precision digit, without rounding or unit conversion. Clock times, dates, identifiers, idioms and literal quotations retain their meaning and protected spelling; incomplete or ambiguous numbers remain unchanged. Nonsemantic hesitation is removed in any sentence position; referential words and opinions remain. Mid-utterance abandoned false starts followed by a complete restatement are dropped while trailing unfinished fragments at the end of the input remain unchanged. Redundant mid-clause ASR punctuation from speaking pauses is removed and mis-punctuated clause or sentence-final marks are corrected according to full-sentence grammar while keeping symbols inside literals, code, paths, URLs and decimals intact. The final rewrite uses this policy. Verbatim mode remains unchanged.

- LRW-11: In polishing mode, the formatter may restore an established English technical term from a phonetic transcription when source context identifies the term unambiguously. This does not authorize translating surrounding Chinese, renaming companies/people/user-named projects, changing literal quotations or overriding an explicit request to retain Chinese spelling. Ambiguous identities remain unchanged. The final formatter uses this policy.

- LRW-12: A final acoustic source can differ from the streaming source shown during speech. Carry earlier recognized, rule-corrected stable text separately as optional `PreviousText`, never substituting generated text for the final recognition. Approved memory relevant to current and earlier recognized sources shares the existing eight-entry recall budget. The GGUF producer nominates same-letter 2..6-word compound spellings in every scene; bounded earlier-source alternatives additionally require independent context confirmation, the same local frame and spelling guards, excluding literal quotes and local spoken corrections. Current-sentence discussion of spelling, literals or word spacing suppresses English contextual nominations conservatively; explicit rejection of earlier recognition suppresses earlier-source nominations. This can leave genuine metalinguistic repair requests uncorrected. If every hypothesis is ambiguous, apply the only legal keep choices through the same source-span validator without selector generation. These are unverified selector choices, not acoustic truth or hard preservation guarantees. Unrelated screen text or prior recognition alone cannot authorize a new spelling.
- LRW-13: A capture session does not complete a preview, so release sends a new rewrite whose text is the recognized source. Reuse of a completed accepted result is allowed only when session/generation and the complete effective source, earlier-source evidence, scene, punctuation mode, terms and context match. Revalidate its raw result before applying punctuation. The punctuation mode is applied to the inserted text. A raw result that fails delivery validation is not cached. Failed, cancelled, truncated, stale or superseded work is ineligible; changed final source, context or punctuation mode reruns inference. Cache state stays in the session and is never persisted.
- LRW-14: Punctuation is a preference used only while `Preferences.Polish` is on, default smart, shown under Settings › Model. The English menu lists smart, full, and omit. Spaces stays a saved preference and a Simplified Chinese option; the English menu does not show it and does not replace a saved spaces value until the user picks another mode. While polish is off the control is disabled and no cleanup prompt is sent. Modes are smart (智能标点), full (添加完整标点), omit (省略句末标点) and spaces (空格代替标点). Smart sends the approved local cleanup prompt unchanged. Full, omit and spaces append one rules bullet to that prompt, requiring complete punctuation: clause pauses become commas or enumeration commas, and a finished sentence ends with a period, question mark or exclamation mark chosen from the words already in the source. No sentence-type flag is sent. After the model returns, delivery validation runs on the raw proposal before punctuation conversion, for the local worker and for cloud polishing. Omit then removes one trailing sentence-final mark (`。！？…` and ASCII `.!?`); a trailing comma is not sentence-final. Spaces replaces punctuation characters with a single space and collapses repeated spaces. Smart and full do not post-edit punctuation. The inserted text uses the mode. Search still strips a sentence-final mark in `FinishScene` after this policy. Vocabulary replacement and the spelling-selection call stay unchanged. The cleanup prompt is a preamble plus one `<rules>` list: shared rules, the scene line, the layout line (omitted for list), then the `han`, `latin` or `mixed` route. User turns and few-shot user turns are `<source>…</source>`.

## Scene selection

The scene sets the layout of a rewrite, never its content. Scenes: `chat` (one plain paragraph, the default), `email` (greeting, body, closing), `work` (natural workplace message, preserving owners, tasks, deadlines and conditions), `prompt` (natural request to a coding agent or assistant, preserving questions and exact code names, paths, commands and error text), `search` (query without sentence-final punctuation) and `list` (numbered lines). Scene hints do not authorize restructuring: default to minimal copyediting and preserve sentence order, voice and existing layout. Multiple clauses, tasks, actors or restrictions alone do not justify bullets. Add list layout only for a clear spoken enumeration, an explicit request for list formatting or the explicit `list` scene; never invent headings or category labels. Already usable text may remain unchanged. These scene categories reflect those Chatterfly presents ([research](../docs/research/chatterfly.md#scene-recognition-and-switching)); search follows its field-type signal.

- SCN-01: With **Match the app** on (default; under Settings › Model while polishing is on), the scene is decided once per session after target capture by `domain.DecideScene`: a scene the user chose for the place wins, then a search field, then the host of the web page owning the focus, then the app's bundle ID, else `chat`. A listed site matches its exact host, ignoring `www.`; workspace domains such as `feishu.cn` also match every subdomain. Off, every session uses `chat`.
- SCN-02: Inputs are metadata only: bundle ID, AX role/subrole and the http(s) host of the outermost `AXWebArea`'s `AXURL`. The host is read only while polishing and Match the app are both on. Field text, page titles, paths, queries, clipboard and history are not read for scene selection. Hosts and bundle IDs stay in session memory and are never logged; the review event reports only the scene.
- SCN-03: The final rewrite of a session uses one scene, preserving work and coding-prompt layouts rather than reducing them to chat/list. Secure fields still fail before capture (DSK-08); no context is read from them.
- SCN-04: Scene tags are prompt structure: a proposal containing any scene tag is rejected as markup. Layout added by a scene passes the same validation as any other proposal.
- SCN-05: Opening the menu bar panel reads the frontmost app's focused field (app name, field type and, under SCN-02's gate, site) and shows its scene with whether it is automatic or the user's choice. Choosing a scene there stores it for that place: the site without `www.` when there is one, else the app, and a search field of that place separately (`domain.SceneKey`). **Automatic** removes the choice. Choices are kept with the preferences on this device; secure fields, Arion itself and unreadable targets show no card.

## Rewrite context

[ADR 013](../docs/decisions/013-rewrite-context-on-device.md) lets polishing read three sources, each with its own switch under Settings › Model, all on by default while polishing is on.

- CTX-01: **Text around the cursor**: up to 200 characters before and after the selection of the captured field, read through Accessibility (macOS). Windows does not read it.
- CTX-02: **Screen content**: visible text exposed by system accessibility APIs in the captured target window only (macOS Accessibility; Windows UI Automation). No screenshots or OCR. Cloud polishing can send this text when its switch is on (CLD-03). Password/hidden/offscreen branches are excluded. Text areas use visible character ranges rather than entire documents. Traversal has a 1.5 s deadline, at most 512 nodes, depth 32 and 32,768 UTF-16 units; exceeding a limit discards the window result and reports failure. Windows may initialize its isolated PowerShell/UIA runtime for at most 5 s before that traversal deadline starts; no target is read during initialization. A READY/GO handshake starts the 1.5 s traversal budget before authorizing the first target access. Caller cancellation applies during both phases, and CTX-04's final wait remains unchanged. A focus change invalidates the read. Applications that expose no text are explicitly unsupported. Sanitized text reaches selection without term extraction; an over-budget model request fails explicitly.
- CTX-03: **Recent dictations**: the last five texts inserted in the same place (`domain.SceneKey`), kept 30 minutes in memory; turning the switch off clears them.
- CTX-04: Secure fields and the password-manager denylist (`domain.ContextDenied`) read nothing. Context is read once per session after target capture, in parallel with speaking; the final rewrite waits at most 1.5 s. It stays in session memory and is never logged or synced; only explicitly selected cloud polishing may send enabled sources to its provider (CLD-03).
- CTX-05: Context is sanitized data, never instructions. Full accessible window text and cursor/history/approved terms reach the shared bounded spelling selection; the formatter receives only the edited source with its scene/script profile. Ambiguous candidate protocols preserve source. Semantic correctness is reviewed, not vetoed by context-overlap string checks. The exact adopted templates and resources are in [local rewriting](../docs/operations/local-rewrite.md).
- CTX-06: **Approved memory** reaches the prompt's terms only for entries whose heard or written form occurs in the recognized source. A changed final request can also recall entries relevant to this session's earlier rule-corrected stable recognition under LRW-12, with current-source matches first and a combined limit of eight (`domain.Vocabulary.Terms`). Generated text never supplies recall evidence, and the prompt does not grow with the vocabulary ([ADR 014](../docs/decisions/014-edit-learning.md)).

## Cloud polishing

Polishing runs on this device by default. The user can choose the cloud engine instead ([ADR 022](../docs/decisions/022-cloud-polishing.md)); everything before the rewrite request and the validation after it stay local.

- CLD-01: The cloud engine is an explicit, persisted choice beside the polishing switch. No request leaves the device while the local engine is chosen, while polishing is off, or before the user connected a provider and chose a model.
- CLD-02: One active connection: a ChatGPT sign-in (browser OAuth with PKCE, loopback on port 1455) or an API key for OpenAI, Anthropic, Google Gemini, DeepSeek or OpenRouter. Each provider's credential is stored separately. A key is stored only after that provider lists models with it. Connecting a provider, or returning to one that already has a credential, makes it active and leaves every other credential in place. Disconnecting deletes only that provider's credential. A credential saved by a build that stored one item is copied to that provider's item on load.
- CLD-03: Both engines use the same staged pipeline and context switches ([ADR 024](../docs/decisions/024-shared-polishing-pipeline.md)). After stop, cloud spelling selection receives the source, scene, recalled approved terms (CTX-06), prior recognized source and enabled cursor/window/history context. Disabled sources are not collected for rewriting or sent. The formatter receives only the edited source and scene/script profile. No audio or app/site identity is sent.
- CLD-04: Both engines polish after stop without live previews (LRW-01). The complete final pipeline (optional selector call, then formatter call) is bounded by 15 s; its proposal passes LRW-05 validation; refusal, missing connection or model, network failure and timeout deliver the completed local cleanup with an explicit outcome (LRW-08). The recipe leaves thinking off. The local worker writes that as its template argument. The cloud request sends reasoning effort `none`, and the provider library translates that into the provider's off switch. A provider that rejects the switch fails the request; it does not run with thinking left on.
- CLD-05: Credentials live only in the OS credential store; the UI state holds the provider, the ChatGPT email and model IDs, never a key or token. A pasted key leaves the view's draft when submitted.

## Runtime requirements

- Work offline after explicit model provisioning; no silent model substitution. The only cloud route is the user's explicit cloud engine choice (CLD-01).
- Model residency and per-session KV state are different lifecycles. Warm sessions may reuse immutable weights, but private context/KV state cannot leak between independent fixtures or users. Cold evaluation releases native model allocations and cache state, then includes reload cost.
- Capture callbacks never execute LLM inference. ASR and LLM workers have bounded queues, cancellation and recorded scheduling/thread policies. Concurrent ASR quality and queue pressure must be evaluated before enabling speculative generation.
- Cancellation tokens alone do not prove safety. Check generation/session/source revision at native preview publication, IME mutation and final target commit.
- No checkpoint, latency target or acceleration provider becomes an accepted product default without actual-host measurements and reviewed model/export provenance. CPU is the comparison baseline; provider acceleration is a separate experiment.

## Evaluation requirements

Use [008 Evaluation](008-evaluation.md) for ASR and native product safety, plus the [rewrite methodology and protocol](../docs/research/rewrite-evaluation.md). The rewrite harness uses the persistent JSONL transport with explicit schema `arion-rewrite-v1`; existing ASR drivers must fail on unsupported rewrite operations.

Evaluate both reviewed gold-text inputs and frozen real-ASR inputs. Hold each source text constant across rewriting variants. Report these strata separately so ASR mistakes do not become alleged rewriting failures or improvements. End-to-end speech evaluation still includes actual audio, endpointing and source-revision changes in the native driver.

Disfluency cases must distinguish hesitation, repetition and self-correction from meaningful uses of the same expressions (demonstratives, comparisons, literal quotes, negation and uncertainty). Report each evaluated recognition language separately. Exploratory text-only probes in another language do not establish ASR coverage or multilingual fidelity; see the [disfluency diagnostic](../docs/research/rewrite-reliability.md#multilingual-disfluency-follow-up).

Factorial comparisons cover rule versus LLM, context, approved memory and scenario hint. A verbatim control exposes unsolicited changes. Separate FP and quantized artifacts with the same reviewed source checkpoint expose conversion/quantization loss; if lineage differs, label the comparison as model/precision rather than causal quantization. Fix prompt/tokenizer/output budgets/no-thinking decoding/provider/threads within a comparison. Report warm/cold residency and solo/concurrent-ASR strata independently.

Automated checks cover protected exact occurrences, declared constraints, unsupported numeral and attack-marker proxies, refusals, delivery coverage, native timing/resource traces and lifecycle invalidation. Meaning, style, fluency and unsupported factual claims require blind independent human review. A release cannot claim semantic success from reference overlap, embedding similarity or an LLM judge alone. Any native stale publication or target commit in the candidate benchmark invalidates the run. Existing output directories, incomplete coverage and changed traces cannot produce a completed report.

## Implementation order

Implemented: source-bound cancellation, isolated worker, KV-reuse parity check and the live development benchmark (LRW-A01–A05); Windows x64 runtime and text-stage lifecycle validation (LRW-A13). P0: reviewed corpus and independent blind review (LRW-A06, RWT-A08); source-checkpoint/export parity; native shortcut/IME acceptance with rendered timing. Scene selection from field, site and app (SCN-A01–A03). Cloud polishing (CLD-A01–A04). P1: Windows local-polishing editor delivery and broader hardware acceptance; native cloud polishing verification (CLD-A05); native site-host verification (SCN-A04); consent-gated context text; ASR-contention and power measurements. P2: broader personalization after harm measurements justify it.
