# 003 Personal memory and self-hosted sync

## Memory

MEM-01: Allowed sync records are user-approved vocabulary entries, explicit correction pairs and per-app style preferences. A record has opaque ID, kind, content schema version, logical revision, origin device, approval provenance and tombstone. Temporary app/selection context is session-only and excluded from persistence/sync.

MEM-02: Learning adds a record only from the user's own correction of text Arion inserted ([ADR 014](../docs/decisions/014-edit-learning.md)). The record applies at once and is shown with an undo; undoing it, or correcting a learned replacement back, removes it. Model guesses, typing that continues or precedes the insertion, deletions, punctuation, changed numbers, sentence-start capitalization, lowered letter case, single Latin letters, grammar-dependent homophones (他/她/它, 的/地/得, 在/再) and rewrites of most of the insertion are never learned. The user can review, remove, export and disable learning/sync independently. CJK correction spans must cover complete words using local boundaries from both versions; changes within a word merge. Ambiguous one-character words are skipped, except complete question-particle phrases; arbitrary neighbor expansion is forbidden. Missing or invalid segmentation reports `words_unavailable`. Vocabulary may influence ranking only within its approved scope.

MEM-04: Memory is bounded. Learned entries unused for 90 days expire and, beyond 2,000 entries, the least used learned entries are evicted; entries the user typed never are. A learned pair whose From matches an entry the user typed leaves that entry unchanged. Recall applies approved entries as whole-word replacements in one pass, and only relevant canonical spellings, at most eight distinct correct terms across the current and earlier recognized source, reach the spelling-selection context. Incorrect aliases never become model spelling evidence.

MEM-06: Settings shows each correct spelling as one term, newest first, holding its incorrect forms and keyboard reading, with searchable correct/incorrect forms, individual alias removal and removal of the whole term. A term is added by its correct spelling alone; incorrect forms are then added on the term itself, one per submission. The vocabulary store adds multiple incorrect forms for one correct term in one atomic operation. Duplicate aliases (case-insensitive) are idempotent; approving an existing learned pair preserves its identity and counters while protecting it from learned expiry. An alias already approved for a different correct term rejects the entire operation explicitly. Empty, control-character and exact identity replacements are rejected. Case-only corrections remain valid. Existing encrypted pair records and per-alias learning, recall counts and undo remain compatible.

MEM-07: Recognition hotwords are correct canonical spellings stored in the same encrypted vocabulary file. Adding a term in Settings saves it as an explicit correct-only hotword, so every term created there is a recognition term; Settings has no separate hotword control or status. A learned correction automatically contributes its correct term; old learned records remain eligible, and explicit approval of a learned pair preserves that eligibility. A manually entered correction pair remains independent and does not automatically become a hotword. Removing, undoing, reversing, re-pointing or pruning a learned pair updates its derived hotword; an independently saved explicit hotword with the same spelling survives removal of that pair. Unapproved proposals and incorrect aliases never enter ASR context.

MEM-08: An approved vocabulary record may carry an explicitly confirmed keyboard Pinyin reading in the existing encrypted file. Bind updates to both record ID and exact current canonical spelling; reject stale, deleted or unapproved targets. Empty removes only the reading. Reinforcement, recall and explicit approval preserve a reading for an unchanged spelling; re-pointing a learned destination clears it. Legacy records without a reading remain unchanged and require no inferred pronunciation. Transport uses lowercase ASCII syllables (including `v` for the keyboard spelling of ü), single spaces, at most 64 syllables of at most six bytes each. This is syntactic validation; the native producer must resolve each syllable against its actual dictionary before generating candidates. Never treat a transport-valid reading as phonetic proof. The app projection reads approved memory, selects only explicitly bound records, sorts by opaque record ID and preserves independent same-word contributions. It exports neither aliases nor ASR counts; an invalid bound record or more than 2,000 projected records rejects the full snapshot. Storage, approved projection, encrypted native caching, macOS transport and application refresh/retry are implemented. Successfully loaded snapshots, including empty deletion, enter one coalescing delivery worker; absent or unreadable app storage must not erase the offline native cache. The vocabulary UI shows a term’s reading beside its correct spelling while Arion’s input method is installed. A new reading binds to the term’s correct-only record, or its first alias record when it has none; a reading already bound to another record of the term stays visible and editable as its own entry. The editor preserves failed drafts and distinguishes invalid input from stale spelling. Windows native delivery and signed installed-host acceptance remain required before shipping shared keyboard terms.

ASR hotword selection is deterministic and bounded independently of the eight-term rewrite recall budget. Explicit user hotwords precede learned terms; within each class, higher use-plus-recall counts precede lower counts, then newer last-use times, exact canonical spelling and record ID break ties. Exact correct spellings share one slot; case-distinct spellings remain distinct. Select at most 64 complete terms, each at most 64 Unicode code points, within 2,048 code points including single-space separators. Learned terms remain limited to the extraction ceiling of 16 code points. Do not truncate terms. Invalid legacy terms are ineligible. Reject invalid UTF-8, controls, Unicode format controls, line/paragraph separators and model-token delimiters `<|` or `|>`. The final selected list is validated again before native transport; an invalid or over-budget request fails explicitly. These are safety bounds, not evidence of improved recognition.

MEM-05: Learning never delays dictation. Following a field starts after the commit returns, each field read has its own time budget, a field that stops answering is abandoned, and the next dictation settles the previous edit without waiting. Memory writes are atomic and durable; a file that fails authentication or cannot be written is left unchanged, learning reports the failure, and dictation continues with whatever memory loaded.

MEM-03: Local writes and outbox creation occur in one transaction. Dictation never waits for network or sync. When sync is disabled, local memory remains available and no outbox uploads occur.

## Relay protocol design

SYNC-01: A self-hosted Go service stores only authenticated ciphertext envelopes and necessary routing metadata. The client encrypts before persistence into the outbox. Auth credentials and encryption keys are separate and neither is stored in repository config.

SYNC-02: Enrollment uses an existing authorized device or a recovery secret to establish group keys. A device has a revocable identity. Crypto library, pairing UX and recovery format are gated decisions; do not implement homemade key exchange. Device registration does not depend on an account: the hosted relay adds OIDC account authorization on top of device authentication, and self-hosted relays may leave it disabled ([ADR 015](../docs/decisions/015-hosted-relay-account-authorization.md)).

SYNC-03: Planned operations are authenticated `POST /v1/sync/push`, `GET /v1/sync/pull?cursor=…`, device enrollment and revoke. Push batches use bounded size and unique operation IDs; retries deduplicate by device and operation ID and return the original result. Pull cursors are opaque, server-ordered and distinct from logical memory revisions.

SYNC-04: Envelopes carry opaque group/record/device/operation IDs, schema version, key epoch, algorithm identifier, nonce, ciphertext, integrity tag and expected server revision. Associated metadata must be authenticated by the client encryption scheme. The relay validates device authentication, shape and revision policy; only authorized recipient clients can validate the E2EE tag and plaintext schema. Exact binary encoding and limits require a protocol fixture before adapter implementation.

SYNC-05: A concurrent edit produces explicit sibling revisions, never silent last-writer-wins based on wall clock. Delete/edit conflicts keep the record suppressed until reviewed. Tombstones are retained until all active devices acknowledge them; revoked/stale devices require full resync. Resolution creates a new descendant revision that is synchronized like a normal write.

SYNC-06: Unknown schema, invalid authentication, revoked device, stale key epoch, invalid tag, replay and cursor expiry are explicit outcomes. Cursor expiry triggers a validated full snapshot path, not clearing local memory. Uncertain push results reuse the same operation ID.

SYNC-07: Revocation rotates the key epoch for future writes and re-encrypts live records before new-device access. Previously downloaded plaintext cannot be remotely erased. Export/deletion/backup procedures disclose this boundary. Sync-disabled and server-deletion are separate visible actions.

## Account authorization

Values for the AstraFoundry issuer, clients, tokens, waitlists and security events are normative in the [platform contracts](https://github.com/AstraFoundry/astrafoundry.si/blob/main/docs/project/platform-contracts.md) (`astrafoundry.si` repository, `docs/project/platform-contracts.md`); [ADR 015](../docs/decisions/015-hosted-relay-account-authorization.md) records Arion's side.

SYNC-08: An `AccountGate` application port resolves each request to a tenant before the relay core runs; the core never reads account data. `noop` (self-host default) uses one implicit tenant and device authentication only. `oidc` requires a Bearer `at+jwt` access token whose signature verifies against the configured issuer's JWKS with the key's `alg` (EdDSA by default; `none` and HMAC rejected), whose `iss`, `aud` (`https://api.arion.astrafoundry.si` for the hosted relay) and `exp` are valid and whose `ent` contains the configured entitlement (`arion.sync.hosted` for the hosted relay), and maps `(issuer, subject)` to a tenant (`account_link` unique on `(issuer, subject)`; `tenant(id, quota, state)`). Device authentication is still required inside the tenant. A missing entitlement, invalid token or frozen tenant is an explicit outcome, never a fallback to `noop`. An account never grants key access: losing every device without the recovery secret makes synced memory unrecoverable.

SYNC-09: With `oidc`, `POST /v1/security-events` accepts RFC 8417 Security Event Tokens pushed per RFC 8935, verified with the issuer's JWKS, `aud` set to the relay's server client and deduplicated by `jti`; it answers `202` with an empty body, or `400` with `{ "err", "description" }` (`invalid_request`, `invalid_key`, `invalid_issuer`, `invalid_audience`). `account-purged` deletes the tenant's ciphertext, routing metadata, devices and account link; `account-disabled` freezes the tenant and revokes its sessions; `account-enabled` unfreezes it; `session-revoked` rejects that subject's tokens issued before the event until the client re-authorizes; `entitlements-changed` (`{ "entitlements": […] }`) is accepted without state change because `ent` is checked on every request. The relay may additionally call the issuer's entitlement introspection as the confidential client `arion-sync` (`client_credentials`, scope `entitlements:introspect`).

SYNC-10: Onboarding offers an AstraFoundry account right after the welcome (Google, GitHub or email, each through the browser) and offers continuing locally without one as a muted gray secondary action. Before browser authentication, the account step shows localized links to Arion’s site-hosted Terms of Use and Privacy Policy. Desktop sign-in uses the system browser, a loopback `127.0.0.1` redirect on a random port and PKCE S256 (RFC 8252); the refresh token is kept only in the OS credential store. Existing credentials restore automatically after startup without blocking local features. Access tokens renew before expiry; transient network failures retain credentials and retry automatically without a Reconnect action. Only missing or invalidated credentials require sign-in. Signing out stops pending restoration and keeps local keys and memory. A signed-in user without the hosted entitlement keeps every local feature. Desktop views do not offer a hosted-sync waitlist. The account client can still resolve the waitlist id from the issuer's Arion catalog entry (key `hosted-sync`), never hardcoded, and join it; a `409` on join means already entitled or already pending. A self-hosted relay remains available.

SYNC-11: Standard desktop packages embed the AstraFoundry center (`https://api.arion.astrafoundry.si`) and its OIDC profile by default. Choosing the default center never enables synchronization or sign-in automatically. Source builds may replace the center and its authentication profile through an explicit public environment-variable allowlist at build time; these values are embedded in the resulting package and require no shell environment when the packaged app starts. Installed packages do not silently change centers from runtime environment variables. A custom device-auth-only center does not require an AstraFoundry account, entitlement or waitlist. A custom OIDC center requires an explicit complete issuer/client/resource/scope/entitlement profile; invalid or incomplete configuration fails the build instead of reverting to AstraFoundry. Credentials, database URLs and private keys are never embedded. Center/account/vault state is isolated so rebuilding against another center never forwards old credentials or automatically migrates memory. Custom-center builds do not use the AstraFoundry update channel unless that channel explicitly preserves their center profile. The [center build profile](../docs/project/central-sync-design.md#distribution-and-build-time-center-profile) defines the selected public configuration contract; build injection, account-profile credential isolation and custom update-channel suppression are implemented; desktop sync integration remains unimplemented.
