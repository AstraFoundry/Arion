# ADR 017: Offline Pinyin keyboard in the macOS IMK host

Status: Accepted; native implementation and isolated engine/AppKit/storage tests complete. System input-source acceptance remains open.

## Context

The user's complete IMK typing alignment request expands the earlier voice-only IME boundary. Retained Doubao and Chatterfly evidence establishes separate local Pinyin engines, incremental composition, paged candidates, partial selection, editing and learning. Their proprietary code/data are evidence, not implementation dependencies ([alignment](../research/imk-typing-alignment.md)).

## Decision

- Add offline Simplified Chinese full-Pinyin typing to the native Objective-C InputMethodKit host, preserving MyGo and the existing voice coordinator. It must type without the menu-bar app running or a network connection.
- Use pinned official librime 1.17.0 through its versioned C API, one process-wide runtime and independent sessions per controller activation. Universal native packaging remains arm64+x86_64. Bundle a complete prebuilt schema/data closure and licenses; no runtime dependency on Homebrew or schema downloads.
- Use an Arion-owned `arion_pinyin` schema derived from the independently licensed `pinyin_simp` full-Pinyin configuration/dictionary, recording exact source revisions, hashes and transitive licenses. Optional stroke reverse lookup is excluded from this schema; full-Pinyin conversion is retained. This is an initial conversion baseline, not a claim of competitor-level accuracy.
- The engine owns segmentation, incremental parsing, raw caret, candidate identity/page, partial choices and remaining suffix. The adapter reads actual engine commits separately from displayed preedit. Candidate selection alone never inserts a preview. Convert UTF-8 engine offsets to UTF-16 before native client writes.
- Keyboard and voice composition have separate owners. Starting voice clears pending keyboard composition; physical typing interrupts a voice session before taking keyboard ownership. Late voice messages or disconnects must never clear a newer keyboard range. Deactivation and Escape discard unconfirmed text. Command-modified host shortcuts relinquish composition before pass-through.
- Use the system `IMKCandidates` window first, with bounded pages, number/mouse selection, engine-driven navigation and stable revision checks. No per-keystroke animation. Chinese/English switching is available from the input menu and Shift+Space; switching clears unconfirmed composition before changing mode.
- Preserve Rime's learning transactions through a custom encrypted user-database backend. Store values in memory and persist only authenticated encrypted snapshots with a separate this-device Keychain key. Do not use stock plaintext userdb, text backups or sync exports. Key/tag/storage errors are explicit; they must not select a plaintext backend or replace an existing vault with a new key. Reset/delete and encrypted backup behavior require independent tests. This extends [ADR 005](005-local-encryption.md), not the account-sync protocol.

## Consequences and gates

Keyboard conversion is a new local candidate producer, not ASR n-best and not a deployed Laya ranker. Full-Pinyin typing, candidate handling, encrypted learning and actual native IMK behavior must all pass [007](../../specs/007-ime-ranking.md) acceptance. The initial lexicon's quality and latency must be measured with original fixtures and real outputs; successful sample conversions do not prove parity. Windows TSF, additional keyboard schemes, cloud candidates and proprietary model equivalence remain separate work.

The encrypted backend uses pinned engine-private C++ interfaces because the public C API does not provide a user-database storage hook. Retain exact header/dependency provenance and ABI checks; upgrade the runtime and adapter together. Native arm64 and translated x86_64 runs each pass 22 actual-engine/AppKit regression cases with synthetic learning keys; x86_64 used Rosetta 2 on arm64, not physical Intel. This verifies the isolated engine/text-system boundary; it does not establish installed IMK dispatch, external-editor behavior or OS-kept-key protection policy. Both ad hoc and Developer ID signed probes on macOS 26.6.2 fail source selection. In the signed run, enable returns `0` but leaves the parent disabled; select returns `-50` despite notarization/Gatekeeper acceptance. Signing is therefore not a demonstrated fix; the TIS state cause and system typing acceptance remain open ([evidence](../research/imk-typing-alignment.md)).

The separate owned-key lifecycle probe verifies actual Keychain provisioning, fresh-process learned ranking, exact-owned-key deletion and fail-closed startup with unchanged ciphertext after key loss. It also exposes a policy gap: the current adapter creates a file-based Keychain item; its requested accessibility attribute is absent. This does not establish the required this-device protection. An explicit Data Protection Keychain add with non-synchronizable `AfterFirstUnlockThisDeviceOnly` policy fails with `errSecMissingEntitlement` (`-34018`) under the existing Developer ID signature; the owned namespace is restored absent.

The corrected provider explicitly selects the Data Protection Keychain, verifies accessibility/synchronization attributes, and rejects existing legacy items with a migration-required error before reading secret data. An owned legacy-item test verifies rejection, no new Data Protection item and no vault bytes; cleanup deletes only the owned item. Native synthetic storage and policy checks pass. No implicit migration or file-based fallback is permitted. Apple's [TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains) requires provisioning-profile authorization for the entitlement-derived Data Protection access groups. The macOS application identifier supplies the default group ([access groups](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps)). The current signing configuration has no Developer ID provisioning profile authorizing the IMK host's application identifier. Supply and embed that profile and pass the real-key lifecycle with verified OS attributes before claiming this-device protection; a Developer ID certificate alone does not satisfy this gate.
