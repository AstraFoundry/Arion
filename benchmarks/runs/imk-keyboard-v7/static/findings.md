# Doubao suffix observer and queued candidate UI refresh

This follow-up binds the same installed DoubaoIme 1.0.2 main/framework carriers as DB-chain2. It uses existing LLVM output checked instruction-by-instruction against the original arm64 bytes, not REA decompilation, runtime execution or a user dictionary. Six focused/reused intervals hash 7,808 bytes and validate 1,952 instructions; five new intervals account for 2,228 bytes / 557 instructions. The large input observer is reused, not claimed as new recovery.

The partial-selection callsite is an input-property observer. It loads the old raw string into x0/x19 at 0x10018a18c, stores the returned suffix at 0x10018a190, and calls 0x100136838 with the OLD string in x0/x1. Inside the observer, [controller + offset(cell0x101341af8)] is the CURRENT raw string. This distinction prevents interpreting the observer's old-value arguments as a new decoder request.

At 0x100137c1c the observer captures the current raw string. It allocates a weak-owner box (weak init at 0x100137c6c), then a closure context holding that box and the two-word string at 0x100137c84/c88. The function pointer is 0x1001aabd0, wrapped in a copied block and submitted to DispatchQueue.main.async at 0x100137d78. The thunk tailcalls 0x100137e04.

The callback weak-loads the controller at 0x100137e3c, returns if it is gone, reads CURRENT raw input at 0x100137e48–54, returns if empty, and checks it against the captured string using bitwise equality or Swift String equality at 0x100137e6c–88. Only the matching-input path refreshes cursor state and calls 0x100188a78 at 0x100137eb8. That helper's own literal names it updateCandidatesResult(). It calls the shipped engine metadata slot +0x230 at 0x100188c38 with startIndex0/count1, then reloads/shows or clears the candidate window according to actual candidate availability. Exported symbol and raw metadata bytes identify +0x230 as getCandidates(startIndex:count:) at 0x24a54; count1 is not a Boolean reset flag.

This queued operation is a guarded candidate UI refresh. It does not itself re-enter the exported convert(input:params:) decoder. Full suffix decoder re-entry through the surrounding selection/engine paths remains bounded unknown. The surrounding-context helper 0x100196db4 is likewise not the decoder. No inference that conversion happens on the dispatch queue is warranted.

The reused observer also clears marked text and controller candidate arrays on an empty current input. At 0x100136b18–38 it increments an integer referenced by offset cell0x101341860 on one transition; its semantic name is not recovered, and the queued callback does not read that cell. This is not proof of a per-session/generation guard. The callback directly establishes weak lifetime and input equality only. Focus-loss ownership, same-string re-entry, cancellation-versus-generation semantics and actual candidate callbacks were not observed. No competitor defect or safety guarantee follows from those unknowns. Arion's session/generation guards are independently designed and tested.
