同僚の「张伟（チャン・ウェイ）」についてメッセージを音声入力しているとします。話しているちょうどそのとき、画面には別の人から届いたチャットウィンドウが開いていました。名前は「张巍（チャン・ウェイ）」。ピンインは同じですが、別人です。

ローカル音声入力で人名や専門用語の誤変換を減らすため、私たちは整文モデルに画面コンテキストを渡す仕組みを作りました。アクティブなウィンドウを OCR で読み取り、画面上のテキストをローカル LLM に渡すのです。実装は数時間で終わり、手元でいくつかの文を試した限りでは、固有名詞がきれいに補正されました。

もしそのデモだけを見て出荷していたら、この機能は2つの逆の方向に同時に問題を起こしていたはずです。

パラメータ数の大きい Qwen3 4B モデルでは、画面にあった张巍のメッセージを参照し、ユーザーが話した张伟についての文を画面の文に置き換えました。しかも当時の出力バリデーターはその置き換えを通過させました。一方、私たちが既定モデルとして出荷している Qwen3 1.7B では、画面コンテキスト、カーソル周辺テキスト、入力履歴をすべてオンにして30件のホールドアウトテストを実行したところ、通過数は9件でした。コンテキストをすべてオフにしても、同じ9件でした。[^context]

![画面上のチャットウィンドウ、张伟についての音声入力、そして Qwen3 4B に置き換えられた結果](./figures/name-swap.ja.webp "バリデーターを変えるきっかけになった反例。Qwen3 4B は画面上の张巍のメッセージを张伟についての入力に上書きし、検証はそれを通しました。コンテキストの加点に上限を設けた後は、同じ提案が却下され、入力はそのまま残ります。")

同じ機能が、大きいモデルでは話し手の意図を書き換え、既定のモデルでは何の効果も出していませんでした。

## 直感と測定結果が食い違った3つの実験

Arion はローカルで動作する音声・ピンイン入力メソッドです。キーを押しながら中国語や英語、あるいは両方を混ぜて話すと、音声認識とオプションのローカル言語モデルが言い直し（「水曜、いや、木曜」→「木曜」）を整えてカーソル位置に入力します。

コンテキスト整文に何が効いているのかを確かめるため、私たちはいくつかのデモで判断する代わりに、30件のホールドアウトセットを事前に凍結しました。そのうち7件は否定例で、無関係なウィンドウ、画面上のプロンプトインジェクション、同音異字の人名、無関係な履歴を含みます。そして3種類のコンテキストを単独でも、組み合わせてもテストしました。[^context]

このセットでは、カーソル周辺のテキストによる通過数の増加は0件、最近の音声入力履歴による増加は1〜2件でした。実際に効いていたのは画面上のテキストです。macOS Vision の高精度 OCR（p50 で 107 ms）と組み合わせると、4B モデルで通過数が5〜6件増えました。大半はウィンドウ内に見えていた人名や専門用語です。高速 OCR（30 ms）に切り替えると中国語が認識できず、そのうち2件を落としました。

しかし、結果を左右したのはモデルのサイズでした。既定の 1.7B モデルはどのコンテキスト形式でも30件中9件のままで、コンテキストを無視しました。約2倍の遅延とメモリを要する 4B モデルにしたときだけ、通過数が9件から16件に増えました。

![Qwen3 4B と Qwen3 1.7B で各コンテキストの有無によるホールドアウト通過数を比べたドットチャート](./figures/context-ablation.ja.webp "30件のホールドアウトで、各コンテキストなし・ありの通過数。4B の伸びはほぼ画面テキストによるもので、出荷している 1.7B はすべてのソースをオンにしてもほとんど動きません。4B の行は用語抽出モード、1.7B の行は1回目の結果です。")

この张伟のケースをきっかけに、私たちはバリデーターでコンテキスト由来の表記に与えるスコアに上限を設け、コンテキストが発話の大部分を置き換えられないようにしました。また、生のテキストではなく抽出した用語リストだけを渡す方式に変えることで、4B の中央値遅延を 1.84 秒から 0.86 秒に短縮しました。そして 1.7B がコンテキストを無視するとわかったため、精度を上げないまま CPU だけを消費する既定設定を出荷せずに済みました。

2つ目の実験では、テキストモデルに発音の手がかりを与えれば認識誤りを直せるかを調べました。

ピンイン、音声から抽出した国際音声記号（IPA）、認識器のトークン信頼度スコアを使い、154件のテストケースに対して Qwen3 1.7B で6つの訂正条件（計924回の実測生成）を実行しました。比較の基準として、LLM を使わない対照群も1行加えました。録音された音声をオフラインの音響モデルでもう一度デコードするパスです。[^phonetic]

| 条件 | 中国語 CER | 英語 WER | 混在 MER |
| --- | --- | --- | --- |
| 生のストリーミング認識 | 8.17% | 7.63% | 36.39% |
| **オフライン音響2回目デコード（対照）** | **5.82%** | **3.97%** | **22.10%** |
| テキストのみの LLM 訂正（Qwen3 1.7B） | 8.42% | 7.53% | 36.39% |
| テキスト + 認識器のトークンスコア | 85.77% | 39.27% | 231.27% |
| 音声 IPA のみ | 314.73% | 334.69% | 275.20% |

下2行の誤り率が 100% を超えているのは、集計スクリプトの誤りではありません。私たちの評価ルールでは、誤り率を 100% で切り詰めることも、失敗したモデル出力を元の認識テキストに差し替えることも行いません。専用の適応をしていない 1.7B モデルに生の log-softmax トークンスコアを渡すと、モデルは同じ語を繰り返し、プロンプトのフィールド名をそのまま出力し、few-shot の例を書き写して 256 トークンの上限に達しました。元のストリーミング認識が正しく認識していた60文のうち、26文を壊しました。「テキストのみの訂正」でもほとんど改善は見られず、無音の4ケースすべてで空文字列ではなく引用符のペア `""` を出力しました。

一方、対照群はすべての指標で上回りました。オフライン音響モデルで音声を再デコードする処理は p50 で 0.13 秒で終わり、3つの誤り率すべてを下げ、60文を改善し、元々正しかった文を1つも壊しませんでした。もしこの対照行がなければ、音響モデルが10分の1の時間で解決できる問題に対して、テキストモデルのプロンプト調整を何週間も続けていたかもしれません。

![各訂正条件で悪化・改善した発話数と、正解を壊した数の発散棒グラフ](./figures/phonetic.ja.webp "154件のテスト発話のうち、生のストリーミング認識と比べて各条件が悪化・改善させた数と、もともと正しかった60件のうち壊した数。害より改善が多いのは LLM を使わない対照だけです。")

3つ目の実験は、公開されている外部実装の再現です。

ピンイン入力側で、Rime 入力メソッド向けに公開されている LLM リランカーが「約 1 ms の遅延」を報告していました。私たちは上流の Lua フィルタをそのまま使い、実際の Rime 候補スナップショット100件とローカル oMLX 上の Qwen3.5-0.8B で再現実験を行いました。[^rime]

第1候補の正解率は100件中56件から45件に下がり、救えたのは3件、壊したのは14件でした。実際の Rime 候補には全文変換と一部のピンインだけを消費する短いプレフィックス候補が混ざるため、モデルが1文字のプレフィックスを先頭に上げるケースが相次ぎ、「朋友（友人）」が「彭」に、「学习（学習）」が「学」に、「电脑（PC）」が「点」に変わりました。

では「約 1 ms」という数値はどこから来たのでしょうか。実測では、ローカルモデルサーバーへの HTTP 呼び出しは中央値で 288.85 ms かかっていました。上流の Lua コードを確認して理由がわかりました。計測に使われていた `os.clock()` は、プロセスの CPU 時間を返す関数だったのです。LuaSocket がモデルサーバーの応答を待ってブロックしている間、Rime プロセスはスリープしているため CPU 時計はほとんど進みません（p50 で `0.787 ms`）。ログには 1 ms 未満と記録されながら、入力しているユーザーは3分の1秒近く待っていました。

![1回のリランク要求のタイムライン：モデルサーバーの生成中 Rime プロセスはスリープしており、CPU 時間と実時間を比較](./figures/clock.ja.webp "1回のリランク要求。os.clock() が数えるのは Rime プロセスの CPU 時間で、ソケット待ちで眠っている間は進みません。だからログは1ミリ秒未満なのに、入力する人は3分の1秒近く待っています。")

さらに生の応答を確認すると、もう1つの問題が見つかりました。Lua パーサーがマルチバイトの UTF-8 中国語句読点をバイト単位の文字クラス `[^...]` に入れていたため、通常の漢字の内部バイトが一致しただけで語が途中で切れていたのです。文脈「婚礼上许下（結婚式で誓った）」とピンイン `shi yan` に対して、モデルは正しく「誓言（誓い）」を返したにもかかわらず、パーサーがバイトを途中で切り、画面には「实验（実験）」と表示されました。89回のモデル応答のうち38回が、このパース処理で一致に失敗していました。[^rime]

![「誓言」と「、」の UTF-8 バイト。共通のバイトが語を切り、Rime は「实验」を表示し続ける](./figures/bytes.ja.webp "「誓言」が「实验」になった理由。Lua の角括弧クラスはバイト単位で一致するため、「言」と「、」が共有する 0x80 が区切りとみなされ、パーサーはモデルの第1候補を捨てます。")

## コードとデモが安くなったとき

体系的に測る前は、3つの案のどれも筋が通っているように見えました。4B モデルでいくつかのウィンドウを試せば画面コンテキストはそのまま使えそうに見え、音響モデルの対照群を置かなければテキスト訂正 LLM もプロンプト次第で改善しそうに見え、`os.clock()` のログにはミリ秒未満の数字が並んでいました。

AI コーディングエージェントとの開発では、こうした見落としがさらに起きやすくなります。Arion のリポジトリのコードの多くは AI エージェントが書き、人がプルリクエストでレビューしています。新しいプロンプトを書く、ONNX モデルを差し替える、コンテキストの取得元を足すといった作業は数分で終わり、どの変更にも説得力のあるデモが付いてきます。

また、コーディングエージェントは目の前のチェックを通すことに最適化します。評価の実行やパイプラインの修正を任せると、モデル出力が不正なときに元のテキストへ戻すフォールバックを足したり、落ちた音声バッファをリトライしたり、不足しているネイティブドライバーをモックしたりするのが、チェックを通すいちばん手っ取り早い方法になりがちです。

コードとデモは安くなりましたが、その変更が次の千文の音声入力を良くしたのか、一部を黙って悪くしていないかを確かめることは安くなりません。見栄えの良いデモやエージェントのフォールバックにだまされないために、私たちはプロダクトの問いを実験のように扱っています。

## 私たちがどう実験を回しているか

### モデルを調整する前にベンチマークを書く

音声の整文モデルを選んだときの手順がわかりやすい例です。プロンプトを調整する前に、テストケースを2組に分けました。24件の開発セットはプロンプトの反復に使い、30件のホールドアウトセットは事前に書いて SHA-256 ハッシュを固定し、完成した候補の比較にだけ使いました。[^live] すべての候補は同じマシン上で本番のワーカーと本番のバリデーターを通しました。

| モデル | ホールドアウト通過数（未整文ベースライン：12 / 30） | 悪化 | 最終書き換え p50 / p95 |
| --- | --- | --- | --- |
| Qwen3 0.6B | 24 | 0 | 0.18 / 0.36 s |
| **Qwen3 1.7B（出荷）** | **27** | **0** | **0.50 / 1.67 s** |
| Qwen3 4B | 28 | 0 | 0.89 / 2.15 s |

4B は約2倍の遅延とメモリで1件多く通るだけです。0.6B は最速ですが3件少なく、節や数値を落とす有害な編集はバリデーターでしか止められませんでした。私たちは 1.7B を出荷しました。

同じレポートはモデルの周りの音声パイプラインも変えました。発話のセグメントごとに認識を確定させると停止後の遅延はわずかに減りますが、セグメント境界で認識誤りが増えます。さらにストリーミング ASR、セグメント単位の Qwen3-ASR、1.7B LLM を同時に動かしたとき、1件の音声が明示的な `AUDIO_DISCONTINUITY` で失敗しました。3つの ONNX Runtime スレッドプールが CPU を奪い合い、音声取り込みキューがあふれたためです。[^live]

リトライで失敗を隠さないルールにしていたため、このエラーはそのまま記録され、セグメント単位の確定方式は見送られました。出荷版のパイプラインは、話し終えた後に発話全体を一度だけデコードします。後日、同じ証拠の連鎖から [ADR 023](https://github.com/AstraFoundry/Arion/blob/main/docs/decisions/023-remove-live-rewrite-preview.md) で発話途中の LLM プレビューも取り除きました。最終パスで常に捨てられ、入力される内容を一度も変えなかったからです。

### 品質と遅延を同じ実行で測る

289 ms かかる外部の LLM リランカーを見送った後、ピンインキーボードには軽量なオンデバイス文脈ランカーを実装しました。同じアプリ内で直近120秒以内に確定した語の並びだけを学習し、一度の確定で上がる順位を2つまでに制限して、一度の選択ミスが第1候補に居座らないようにしています。[^imk]

50組の同音語・3シードのテストで、初出時の正解率は 14% で同じですが、2回目以降の出現では、従来の頻度学習だけだと異なる文脈の同音語が互いの履歴を上書きし合って 32.2% にとどまりました。文脈ランカーを有効にすると、2回目以降の第1候補正解率は 88.7%（MRR は `0.612` から `0.933`）に上がり、47組が改善、悪化は0組でした。

同じ実行でキー入力ごとの遅延も測りました。文脈ランカー自体の処理は1キーあたり 0.02〜0.06 ms でしたが、最初の計測では文字キー全体の p95 遅延が 2.92 ms ありました。サンプリングプロファイルで、確定のたびに候補ウィンドウをウィンドウサーバー上で並べ直す `orderFront` が文字キーのコストの大半を占めているとわかりました。待機中はウィンドウを透明かつクリックスルーにし、2秒間操作がないときだけウィンドウリストから外すように直した結果、文字キーの p95 は 0.81 ms に下がりました。[^imk]

### 失敗を残す 98 MB の再現可能なアーカイブ

仕様 008（`specs/008-evaluation.md`）では、失敗やキャンセルされた実行はその状態を保ち、不完全な実行から完了レポートは作れず、失敗したモデルの出力を原文に差し替えて表をきれいに見せることもしないと定めています。[^eval]

発音実験で Qwen3 4B の実行を途中で止めたときも、完了していた2回の生成は `cancelled_by_user` としてアーカイブに残り、レポートは完了した 1.7B のチェックポイントだけを使っています。

ベンチマークのコーパス、ケースごとの生出力、ウォームアップ、失敗した試行、録音した音声、正確なスクリプトとプロンプトはすべてリポジトリの `benchmarks/` にバイト単位の SHA-256 識別子付きで置いてあります。1,062 ファイル、約 98 MB の証拠です（モデルの重みと個人の録音は含みません）。[^archive] モデルを読み込まずにアーカイブを検証し、レポートを再構築できます。

```sh
pnpm bench:archive:verify
pnpm bench:archive:report --out .workspace/archive-report-repeat
```

評価プロトコルは、放っておくと実行ごとにずれていく統計上の細部も固定しています。一つのテキスト正規化、総誤り数を総参照単位で割るコーパス誤り率、話者クラスター単位の対応付きブートストラップ区間です。テストの正解は推論にも記憶にもコンテキストにも入らず、テストデータから学んだ記憶はそのまま拒否されます（`EVAL-A04`）。[^method]

### 結果をルールにする

測定は一度に一つの問いにしか答えません。結論を残すために、決定はすべて三つの場所に明文化します。

`specs/` の仕様はプロダクトが満たすべきことを `EVAL-A04` や `LRW-A05` のような受け入れ ID 付きで書き、実際の OS でシナリオを通過して初めて完了とします。`docs/decisions/` の意思決定記録は理由を残します。現在28本あり、削除されずに置き換えられていきます。整文も、入力前のレビュー（ADR 008）から、話しながらのプレビューと自動入力（ADR 011）、そして発話中プレビューの廃止（ADR 023）へと進み、どの段階もそれを正当化した証拠にリンクしています。そして `AGENTS.md` と `CLAUDE.md` は、こうした教訓をコーディングエージェントがコードを書く前に読む制約に変えます。推論の証拠をモック出力で代用しない、理解していない問題を隠すフォールバックを書かない、ドキュメントはコードと同じ変更セットで更新する。

ドライバーやモデルが欠けていれば実行は目に見える形で失敗し、欠けている機能が通過したテストとして報告されることはありません。エージェントにとっても、いちばん手軽な道が誠実な修正になります。

## まだ証明していないこと

どのレポートも冒頭で限界を書いています。現時点では次の三つが残っています。

ほとんどのコーパスは開発者一人が作成し、音声の多くは合成または読み上げです。公開済みのテストセットは回帰データとしては役立ちますが、もう一度まっさらなブラインドテストセットになることはありません。

書き換え品質は完全一致による代理指標で測っています。意味、文体、幻覚についての盲検の人手評価（`LRW-A06`）は、まだ閉じていないリリース条件です。

ほとんどの数字は Apple M4（32 GiB）の1台で取ったものです。Windows の経路は、多くがコンパイル確認と単体テストだけで実測していません。

## ほかのチームに伝えたいこと

ローカルモデルとコーディングエージェントでプロダクトをつくるなら、ボトルネックはもうコードではありません。つくる前に「良くなった」とは何かを決め、ホールドアウトセットをハッシュで凍結してください。一度に一つの要因だけを変え、新しいモデルを使わない対照を残してください。成功と同じくらい丁寧に失敗を記録し、決定は次のエージェントが読む場所に書き、古い決定は消さずに新しい決定で置き換えてください。それだけでプロダクトが良くなるわけではありませんが、自分をだますことはずっと難しくなります。
