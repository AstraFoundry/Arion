# ONNX models for local scenario rewriting

This document records the initial source/artifact metadata study, before weight provisioning or inference. Follow-up [Qwen development diagnostics](qwen-pipeline-diagnostics.md) execute selected CPU packages and retain their measured aggregates separately; they do not establish production packaging or semantic quality. The accompanying [candidate catalog](https://github.com/AstraFoundry/Arion-evaluation) (`benchmarks/catalogs/rewrite-model-candidates.json`) is research metadata, not the production model registry. All candidates remain unapproved.

## What realtime means here

A causal LLM can emit output tokens while decoding. That does not make it an incremental speech recognizer or guarantee safe rewriting while the speaker changes an earlier phrase. Scenario rewriting consumes a bounded text snapshot after a stable phrase or explicit stop. Each request carries the session, transcript revision, context revision, mode and generation ID. New contradictory ASR evidence invalidates the old rewrite. Tokens can update an owned preview; only validated final text can reach the target.

Measure input-to-first-visible-token, input-to-validated-final-text and last-voiced-sample-to-review-ready separately. A fast token rate cannot compensate for long prompt prefill, late endpointing or inaccurate first output. Evaluate both phrase-boundary scheduling and stop-only scheduling; do not launch a fresh autoregressive job for every ASR token.

These are Arion design choices, not observed competitor internals. Existing [speech research](on-device-speech.md), [model requirements](../../specs/006-models.md) and [evaluation requirements](../../specs/008-evaluation.md) still apply.

## Runtime paths and compatibility boundaries

| Path | What it supplies | What Arion must supply |
|---|---|---|
| ONNX Runtime C/C++ | Graph execution and execution-provider selection | Tokenizer, chat formatting, prefill/decode loop, sampling, masks/positions, cache ownership, stopping and cancellation |
| ONNX Runtime GenAI C/C++ | A model-package contract and generation machinery | Compatible export/config/tokenizer bundle, approved prompt/context policy, revision control, bounded generation and validated delivery |
| Optimum ONNX | Export and Python reference tooling | Native deployment and any generation logic that lives in its Python wrapper |

GenAI has an official [C API](https://onnxruntime.ai/docs/genai/api/c.html). Use a small native infrastructure adapter or worker behind domain ports; its published API matrix does not list Go. Go/cgo can call a C ABI, but that is an Arion integration responsibility. The upstream runtime and export tools are not a reason to ship Python or replace MyGo. [GenAI API/platform matrix](https://github.com/microsoft/onnxruntime-genai/blob/1d67be30e5b1ed0c264f6f41c598f85157e8288b/README.md), [ONNX Runtime C integration](https://onnxruntime.ai/docs/get-started/with-c.html).

A `.onnx` filename establishes a graph artifact, not compatibility with GenAI. The package must match [GenAI configuration](https://onnxruntime.ai/docs/genai/reference/config.html): model type, exact input/output names, tensor dtypes/shapes, cache layout, tokenizer and stop IDs. External weight files must be included and hash-verified. A Transformers.js example proves that wrapper's intended interface, not native GenAI parity.

Context7 was queried first for GenAI, ONNX Runtime and Optimum. The Optimum query returned no matching documentation; official current docs and pinned upstream source were used for that gap. The inspected `optimum-onnx` v0.1.0 source registers `qwen3` and `qwen2` causal-generation configurations. Export-with-past is documented, but the Python `generate()` method is not embedded into the graph. [Pinned exporter](https://github.com/huggingface/optimum-onnx/blob/d2328e386a81b0970a458a7570a38b131414edc6/optimum/exporters/onnx/model_configs.py), [export/cache documentation](https://huggingface.co/docs/optimum-onnx/onnx/usage_guides/export_a_model).

Runtime provenance in the catalog pins GenAI v0.17.0 (`1d67be30e5b1ed0c264f6f41c598f85157e8288b`), an observed ONNX Runtime v1.29.1 tag (`d9d3b2fc25558db20900cb71865ffeb2348a3385`) and Optimum ONNX v0.1.0 (`d2328e386a81b0970a458a7570a38b131414edc6`). These are research source references, not an asserted compatible binary set. Pin the actual ORT dependency, compiler, generated operator requirements and native-library hashes when building a driver. [GenAI release](https://github.com/microsoft/onnxruntime-genai/releases/tag/v0.17.0).

Qwen3's inspected CPU GenAI packages name their model `qwen3`, declare attention cache input/output names and include `chat_template.jinja` plus tokenizer assets. This makes them a concrete first loading experiment. Their existence does not prove a particular GenAI version can run them correctly on Arion's target hosts. Disable thinking through the model's exact chat template; filtering `<think>` after generation does not recover its spent latency. Pin sampling settings and seeds; deterministic greedy decoding is an experimental control, not a claim to reproduce vendor-recommended sampling. [Qwen3 thinking/sampling contract](https://huggingface.co/Qwen/Qwen3-0.6B/blob/c1899de289a04d12100db370d81485cdf75e47ca/README.md).

Qwen3.5 uses Gated DeltaNet blocks interleaved with attention, so its state cannot be represented by a generic attention-only cache adapter. Importantly, the inspected GenAI v0.17.0 builder **does** contain Qwen3.5 routes, including `qwen3_5_text`; architecture support is not the missing element. Either build a matched native GenAI package with the pinned builder or implement and verify the community graph contract. The community 0.8B example uses Transformers.js `@next`, WebGPU and multiple submodels; do not equate that example with a native CPU load test. The small original cards default to non-thinking mode, but Arion should still pin that policy explicitly. [Pinned GenAI builder](https://github.com/microsoft/onnxruntime-genai/blob/1d67be30e5b1ed0c264f6f41c598f85157e8288b/src/python/py/models/builder.py), [Qwen3.5 export contract](https://huggingface.co/onnx-community/Qwen3.5-0.8B-ONNX-OPT/blob/969350d5f4647ec9ac277110f8974c65d8c10e4b/README.md).

## macOS and Windows deployment

Start with CPU as a shared, auditable baseline. The GenAI support matrix lists Mac and Windows plus CPU, but is not a promise that every architecture/provider combination or downloaded export is supported. Build or verify native assets for macOS arm64/x86_64 and Windows x86_64 separately. Keep Windows arm64 a separately verified target. Record compiler/runtime dependencies, exported C ABI, dynamic-library load paths, notices, signatures and clean-machine load evidence. Check native teardown after repeated cancel/model-switch cycles; Go GC is not native resource ownership. [Native build guidance](https://onnxruntime.ai/docs/genai/howto/build-from-source.html).

CoreML is an ONNX Runtime execution provider, not a listed GenAI provider in the inspected matrix. Current ORT documentation says official macOS arm64 CPU packaging jobs include CoreML; verify availability in the exact library. Dynamic shapes can hurt performance, and unsupported nodes can partition onto CPU. Profile actual graph coverage, transfers and cold compilation; do not promise Apple Neural Engine acceleration from provider availability. [CoreML provider](https://onnxruntime.ai/docs/execution-providers/CoreML-ExecutionProvider.html).

DirectML remains supported but is in sustained engineering; official docs direct new Windows deployment development toward WinML. DirectML requires sequential execution, no memory-pattern optimization and no simultaneous `Run` calls on one session. Compare a reviewed DirectML/WinML package against CPU before adopting it; a model's CUDA export is not an assumed DirectML-compatible asset. GenAI also lists WebGPU, but a Transformers.js browser example is not evidence of native-Go packaging or latency. [DirectML provider](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html).

Inspect telemetry as an actual runtime build property. The pinned GenAI build contains `ENABLE_TELEMETRY` branches. Arion should explicitly disable telemetry in its build and verify both disconnected inference and connected network observation. Review ORT logging/telemetry and all native dependencies as well. No claim is made here that the downloaded stock runtime sends user text. [Pinned build configuration](https://github.com/microsoft/onnxruntime-genai/blob/1d67be30e5b1ed0c264f6f41c598f85157e8288b/CMakeLists.txt).

### Coexistence with the current ASR runtime

The current desktop [module](../../apps/desktop/go.mod) pins `sherpa-onnx-go` v1.13.8. Its macOS cgo files link both sherpa and ONNX Runtime and add a module-cache rpath; its Windows cgo files also link both libraries. The locally installed arm64 sherpa library's Mach-O dependency is `@rpath/libonnxruntime.dylib`, and its bundled ORT has that same install name. The Windows package contains `onnxruntime.dll`. These are inspected dependency facts, not a reproduced collision. [Pinned macOS link flags](https://github.com/k2-fsa/sherpa-onnx-go-macos/blob/v1.13.8/build_darwin_arm64.go), [Windows link flags](https://github.com/k2-fsa/sherpa-onnx-go-windows/blob/v1.13.8/build_windows_amd64.go).

Do not assume an independently packaged GenAI ORT can coexist safely in that process: equal install names/DLL names, loader search order and C API requirements can bind a consumer to an unintended build. Renaming a file alone does not establish independent symbol/dependency resolution. Before sharing a process, either prove one reviewed ORT build satisfies both engines and rerun ASR/LLM parity tests, or fully verify separate native dependency identity and resolution on each OS. Record the actually loaded paths, library hashes, `OrtGetApiBase` runtime version and required C API versions rather than inferring the runtime from a Go module tag.

A dedicated LLM inference worker is a proposed evaluation option while coexistence is unresolved: it owns its exact runtime directory and native lifecycle; the desktop communicates over a bounded local channel carrying revisioned jobs. Crash/cancel cleanup and extra process/RSS/startup/IPC overhead must be measured. This is not a production isolation decision. Whichever route is selected, replace development module-cache rpaths with reviewed bundle-relative dependencies before shipping; test macOS architecture/signing/notarization and Windows trusted DLL search/dependent compiler runtime on clean machines without the Go cache present.

## Required integration and selection gates

1. **Provenance and permission:** exact original/export revisions, source license and conversion notices, every graph/external-data/tokenizer/template hash, exporter versions, quantizer/calibration corpus, runtime version and ABI. Missing conversion license metadata remains a review item.
2. **Native/reference parity:** Chinese, English, mixed script, emoji, code, whitespace and special-marker test vectors. Compare token IDs, rendered prompts, prefill/decode shapes, positions/masks, cache reuse, logits within declared tolerances, final stop behavior and Unicode streaming boundaries against a pinned reference. Compare quantized output to a floating-point reference separately.
3. **Bounded operation:** declare application limits for context tokens, generated tokens, elapsed time, pending jobs and memory. Do not inherit the bundle's 40,960 or 131,072 `max_length` as the application's rewrite budget. Validate overlong requests explicitly. Fresh session/context revisions must never reuse another user's or stale turn's cache.
4. **Rewrite policy:** router and rewriter are separately observable stages. Modes distinguish faithful cleanup, context correction and explicit style rewriting. Pin app/field metadata allowlists, relevant approved memory, prompt/template version, protected facts and output validation. Text from selection/context is untrusted data, including apparent instructions.
5. **Quality:** compare raw ASR, rules-only, rules+LLM and optional ranker+LLM. On fixed gold transcripts isolate rewriting; on ASR replays measure compounded errors. Report facts added/deleted, numbers/names/negation preservation, unnecessary-edit rate, task/style compliance and reviewer preference with language/domain strata. CER/WER alone penalizes legitimate stylistic paraphrases and cannot decide rewrite quality.
6. **Streaming experience:** trace ASR revision, rewrite scheduling, prompt-ready, prefill, first-token, last-token, validation, actual preview render and target commit. Report revision withdrawal, stale-result rejection, cancellation latency, generated-token waste, per-stage p50/p95/p99 and speech-to-review latency. Measure CPU/RSS/energy plus concurrent ASR queue lag and dropped frames.
7. **Product delivery:** offline behavior, secure/unknown-field context exclusion, prompt injection, focus/mode changes, cancel/restart, repeated commit attempts, IME composition ownership and deadline/limit failures. Unsupported generation, timeouts and validation failures are visible outcomes; never silently change provider/model or publish unvalidated partial text.

Select Qwen3 0.6B and 1.7B CPU GenAI packages as the initial **experiments**, with Qwen2.5 controls and Qwen3.5 challengers once the exact state/export route is validated. Keep SmolLM2 as an English control; Phi and Gemma are optional footprint/terms tradeoff comparisons. There is no established model winner or realtime guarantee until the complete speech-to-preview-to-commit evaluation passes on both target operating systems.
