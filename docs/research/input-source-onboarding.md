# Competitor input-source onboarding

## Scope

This bounded static follow-up inspects installed Doubao **1.0.2 (1)** and Chatterfly **1.0.7.13415**, plus the separately retained **1.0.6.13398** Chatterfly installer. Their installer versions are not interchangeable. No competitor, script or helper was executed; no input-source or preference state was changed. The [ledger](evidence/input-source-onboarding.json) binds current carrier/slice hashes, 15 focused intervals (7,628 bytes / 1,907 instructions), exact literal/metadata bytes and the retained script digest.

REA 6.4.0 `inspect_macho` records are retained locally. One actual REA/Ghidra 12.1.4 function dossier, `ev_b188b1ff58f09de8a3eef2b118be81a06c685a77edcbb97287e439cf9c5253c7`, analyzes the installed Chatterfly selector's byte-matching arm64 slice. Other instruction findings are ordinary LLVM observations checked against original bytes, not REA decompilation. The first attempt on the universal selector was explicitly rejected; thinning resolved that architecture limitation.

## Doubao: registration, notification and selection are separate

Installed `DoubaoImeSettings` has SHA-256 `13fff30333c99fcd706e30f1e8408d49d04cb5748146a8befa72dff381f57762`. Its `InstallerInputSourceHandler` contains this reachable sequence:

| Step | Concrete anchor |
| --- | --- |
| Arrange callbacks | `enableAndSelectInputMode(needCallback:completion:)` callsite `0x1001cda20` registers enabled-source notification/retry support when requested. |
| Register bundle | Call `0x1001cdf74` at `0x1001cda34`; logs distinguish successful registration, a nonzero return with an already-resolvable source, and failure. |
| Switch away first | `changeToSystemInputMode()` at `0x1001ce5d0` resolves/selects ABC. |
| Enable | `enableInputSource()` at `0x1001ce8ec` resolves the source, handles already-enabled/missing cases, and invokes `TISEnableInputSource` at `0x1001ceb10`; off-main callers marshal synchronously to the main queue. |
| Confirm enabled | `completeIfEnabled()` at `0x1001ceca8` checks actual enablement and logs “input source is not enabled yet” rather than treating registration alone as completion. |

The shipped settings URLs include both `x-apple.systempreferences:com.apple.Keyboard-Settings.extension?InputSources` and `x-apple.systempreferences:com.apple.preference.keyboard?InputSources`. Their exact literals are bound; the active OS-version branch is not recovered. A separate script-construction surface at `0x1000e53b8` reveals an anchor in System Preferences' keyboard pane and activates it. This is not evidence of clicking consent controls through System Events.

The preference read at `0x1001c7908` synchronizes the `com.apple.inputsources` domain, then uses `CFPreferencesCopyValue` for `AppleEnabledThirdPartyInputSources`. This is a query, not a demonstrated consent-list write. The bounded trace does not establish that the entire product never writes other preferences.

After successful selection, `reloadInputMenu()` constructs an `NSTask` for `/usr/bin/killall`. Original static argument-array bytes identify **TextInputMenuAgent** and **TextInputSwitcher**; task launch/wait/status handling is reachable. This process refresh is static product behavior, not evidence that it is required or sufficient to repair modern activation. Doubao's outer installer copy/privilege/button chain is not recovered from the installed settings bundle.

## Chatterfly: explicit enable UI and asynchronous completion

The current host SHA-256 is `1b8277d1ac41bba3db6a15cd292fb108c8f38f748a94d29fcea837df25c7bd42`. Its `SGTools` separates enablement, source-list checking and selection. `trySelectYuanbaoOnceAndReport` at `0x10004e510` finds the Pinyin mode and calls TIS selection. Only return `0` marks selection successful, stops retrying, reports success and invokes refresh. `startSelectRetryFlow` at `0x10004e64c` observes `kTISNotifyEnabledKeyboardInputSourcesChanged` and installs a repeating timer; the timer also has timeout/failure handling. Enable operations marshal to the main thread.

`isThirdPartyInputSourceEnabledInInputList:` at `0x10004dfdc` reads `~/Library/Preferences/com.apple.inputsources.plist` and examines `AppleEnabledThirdPartyInputSources`; no consent-list write occurs in that bounded method. A separate legacy `selectShowInputMenuInMenuBarNeedsReload:` method conditionally inserts `TextInput.menu` into **com.apple.systemuiserver menuExtras** and writes that plist (`0x10004f598`), or uses an `open` command. That changes menu presentation, not the third-party authorization list.

The post-selection delayed refresh at `0x10004e9c8` reaches process handling for **pboard** and **TextInputMenuAgent**. The installed `InstallerSelector` helper (SHA-256 `14616dc101c29b3074b1b50c1f7cae48a6cfc8c123297d0ac1eab7d03d3b8ee2`) itself only enumerates existing sources, checks Pinyin availability, selects it and emits a success notification after TIS returns zero. It is not an all-purpose privileged installer or an authorization bypass.

The retained **1.0.6.13398 installer** provides concrete visible UI evidence. UTF-16 CFString bytes decode the button as “去启用”, the instruction as adding Chatterfly to the input-method list, and the fallback as “若未能自动启用，请前往「系统设置 > 键盘 > 输入法」手动添加 Chatterfly，详情可查看”. `enableButtonClicked:` at `0x100059e24` enters an enabling/debounce state and calls its delegate; enabled-source notifications, a manual-tip label and a switch-check timer advance the guide only after observed state changes. Its `enableInputGuideNew`/`enableInputGuide` images are named in the UI code. These facts do not establish the newer installed version's exact visible text.

Its shipped `install.sh` moves a staged app into `/Library/Input Methods`, installs/registers LaunchAgents, clears quarantine attributes and refreshes processes/menu state. The script assumes privileged installation and includes destructive replacement/migration behavior; it was only read. The original pass did not trace the outer installation chain; the follow-up below resolves the privileged helper and post-install registration paths. Commented selection-helper commands are not counted as executed steps.

## Implication for Arion

“One click” covers several stages: file placement, TIS registration, user-visible enablement, mode selection and onboarding completion. Competitor code also waits for state changes and supplies manual instructions; a zero registration/enable status does not establish completion. Static process refresh and legacy plist manipulation do not justify copying those interventions into Arion as proven repairs. Actual first-install consent behavior, login/cache effects and competitor success on this macOS session remain unobserved. Arion's previously deferred system acceptance remains separate from this read-only investigation.

## Chatterfly installation-to-registration follow-up

## Upgrade replacement and runtime handover

The [update ledger](evidence/input-method-updates.json) binds the installed Doubao 1.0.2 update script and the retained Chatterfly 1.0.6.13398 installer script. Two additional Chatterfly installer intervals (170 instructions) were checked against the retained original arm64 bytes. These are ordinary static script/LLVM observations, not new REA decompilation or a performed competitor update. The Doubao main executable still matches the earlier retained identity.

- **Doubao:** `Contents/Resources/update.sh` prepares `Contents_update`, checks directory permissions and other users' active processes, terminates the current user's matching IME/settings processes, and waits for their absence before replacing `Contents`. It moves old contents to `Contents_backup` and attempts restoration if promotion fails. Process exit timeout aborts the replacement. The script also refreshes SystemUIServer; this does not prove that such a refresh is necessary or sufficient. The updater/helper's successful relaunch and input-source restoration after the script exits remain unverified.
- **Chatterfly:** before the privileged helper, the installer calls `switchAwayFromInstalledInputSourceIfNeeded`. Its retained script stops IME/helper/service processes (TERM followed by a delayed KILL), unloads the prior task-manager LaunchAgent, removes the old complete app bundle and moves in the staged app. It then replaces/restarts service agents. These destructive migration choices are competitor observations, not Arion requirements.
- **Chatterfly upgrade completion:** `p_executeUpgradeInstallPostActionsIfReady` waits for both installation-script completion and its progress gate, checks the upgrade branch and a one-shot guard, then starts a repeating 0.5-second timer. `p_pollInputSourceAvailable` checks Pinyin availability, attempts `selectSogouInputMethodNow` and stops polling; after ten unsuccessful availability observations it opens the enablement guide. Availability followed by a selection attempt is not proof of a verified new-process build or successful host composition.

### Arion comparison

Before the upgrade repair, `macos.InstallIME` staged and replaced the complete bundle with rollback for registration/enablement failures, then requests `forceTerminate` on matching input-method applications. It ignored the returned count, did not await process exit, did not switch away before replacement or restore prior selection afterward, and did not verify a newly connected host/build before reporting completion. The repaired lifecycle is specified in [ADR 006](../decisions/006-macos-input-method-host.md). A selected TIS source alone is not evidence that the desktop process has a connected IMK client.

In the investigated local failure, the installed executable and signature resource list match the copies bundled in `/Applications/Arion.app`; the input-method process exists. The desktop log records `ime_listen` with `IO_FAILED`, no process owns its `ime.sock` listener, and a bounded connection probe returns `ECONNREFUSED`. This establishes a stale local IPC endpoint in that session, independently of successful file replacement. Restarting only the IMK host cannot restore a listener that the desktop failed to create.

The recommended upgrade transaction is: stage/validate the new bundle → cancel owned composition and remember actual selection → switch away and await old-host exit → replace/register/enable with rollback → restore Arion only if it was previously selected → verify a new host connection and compatible build before reporting readiness. Desktop restarts must also safely recover an orphaned IPC endpoint without removing a live listener. Failures at process exit, file promotion, registration or reconnection must remain distinguishable. The Arion repair now implements this lifecycle; [native verification](../quality/e2e.md#input-method-upgrade-verification) records the subsequent signed-package smoke checks. No competitor installation or update was executed.

## Alignment plan for the supplied Chatterfly installer

The user-selected `/Users/steven/Downloads/Chatterfly_V1.0.6.13398.app` matches the retained installer and privileged-helper SHA-256 identities. All 11 installer instruction intervals in the registration ledger were checked again against its executable bytes. `Resources/ChatterFly.zip` contains a 1.0.6.13398 host declaring `smSimpChinese`; its `install.sh` matches the retained script byte-for-byte. The existing four REA/Ghidra dossiers therefore apply to this exact selected installer. A fresh installer `inspect_plist` record is retained at `.workspace/research/input-source-category/chatterfly-installer-plist-rea.json`. This remains static analysis, with no installation or authorization performed.

The target experience is an explicit **Enable Arion** action that continues through registration, native authorization, observed enablement and selection; manual Settings navigation is recovery when those stages remain incomplete. Current `bootstrap/actions.go` starts asynchronous installation correctly. `infrastructure/macos/native.m` already registers the installed bundle and enables parent before child. `bootstrap/platform_darwin.go` collapses copied/undiscovered and registered/disabled into `pending`; `ui/features/keyboard/keyboard.go` gives pending/enabled sources a Settings navigation action, without a registration retry or selection action. `refreshInputMethod` only publishes observed state. `InstallIME` restores selection for a previously selected upgrade but does not select a first install. Onboarding already requires actual selection and must retain that gate.

Recommended dependency order (proposed behavior, not implemented):

1. **P0 — Define setup intent and observable stages.** Update IME-01 and ADR 006 for selection initiated by the explicit enable/setup action; current requirements reserve source choice to OS controls. Preserve distinct copied/undiscovered, registered/disabled, enabled and selected states. Report observable facts rather than inferring whether a consent prompt was accepted. Cancel setup continuation when the user defers, removes the host or leaves the flow.
2. **P0 — Add a shared activation operation.** After installation, or an explicit pending-state retry, validate the installed payload, register its URL, request parent/child enablement on the main thread and observe subsequent state. Retry must reuse valid installed bytes, not invoke replacement or require remove/reinstall. Serialize install/update/remove/activation operations. Check current state before each stage; already-selected sources complete without another switch.
3. **P0 — Continue to selection during the requested setup.** Observe enabled-source changes before requesting enablement; retain bounded polling/deadline handling. Once actual enablement is observed, request selection and verify the selected source independently of the API return. Stop retries on success, cancellation or deadline. Keep native authorization visible. This continuation applies only to the active explicit setup attempt, not ordinary background refresh.
4. **P1 — Present stage-specific recovery in the shared setup controls.** Pending exposes retry/enable plus Settings help; enabled exposes switch/use; selected shows completion. Distinguish discovery, enable-request, selection and host-connection failures in diagnostics. Both onboarding and Settings use the same feature. Add-list navigation remains a documented manual recovery path after an incomplete attempt, not the sole action immediately after copying.
5. **P0 — Verify on actual macOS with a signed release.** Capture first installation, system authorization, source discovery, observed enablement, verified selection and real editor input. Also cover denial, cancellation, explicit retry, enabled-but-unselected recovery and selected-source updates. API success, a selected source and an IPC connection are separate checks. Isolated tests must exercise transitions and cancellation; they do not establish OS acceptance.

Chatterfly installs system-wide through a privileged helper while Arion installs per-user. This difference is real, but neither this static comparison nor the earlier Arion visibility controls establish it as the failure cause. A decision to change installation scope requires a separate controlled OS experiment and architecture decision. Competitor process killing, quarantine removal and legacy preference edits are likewise not established prerequisites for the desired setup flow.

Observers installed before requests, bounded retries, deadlines and recovery buttons are engineering choices supported by competitor static evidence, not an Apple-prescribed wizard. No consulted official document establishes the precise modern first-install consent trigger, automatic enablement after Allow, guaranteed one-click setup or a way around language grouping. The proposed automatic switch must be conditional on observed enablement within an explicit setup attempt and still requires actual-OS acceptance.


## Implemented activation alignment and native acceptance

The proposed gaps above are implemented in `bootstrap/actions_ime.go`, `macos.ActivateIME` and the shared keyboard controls. Successful registration with delayed discovery retains validated bytes; installed-source retry never replaces them. First installation continues into bounded activation, while upgrades preserve prior selection. Enabled/selected notifications wake re-query; native queued selection checks cancellation. Deferral, page/window exit and quit revoke continuation. Discovery, enablement, selection and expected-host failures have separate recovery copy and content-free diagnostic stages. Onboarding blocks Continue while activation runs or a setup error remains, including selected-but-unconnected hosts; selected failures retain an enable/retry action.

[The native acceptance record](../../benchmarks/runs/ime-activation-v1/README.md) retains production-adapter results, exact package identities, focused source snapshots, check logs and UI captures. On this macOS arm64 account, existing activation, repeated activation, cancellation, signed upgrade preserving an unselected source, and remove/reinstall → registered-disabled → activation → selected/connected passed. Retry left installed bytes unchanged. The signed nested host received real IMK key events in an owned AppKit editor: `nihao` formed marked text, Space committed `你好` exactly once, and a subsequent `ni` + Escape preserved that commit. Typing used an isolated keyboard profile, which was removed after the host/fixture stopped. The original source was restored. The signed/notarized main app and matching host were installed; the previous main app is recoverable in the ignored local backup.

A first isolated direct-launch attempt reached selected state but timed out on expected-host connection. The failed raw result remains in the run. LaunchServices startup with an explicit test-profile environment and an independently observed hello preceded the successful isolated attempt; this is not evidence that arbitrary direct launches preserve that environment. The background main app could not be attached by CUA for live GUI clicks; action wiring and real window lifecycle are established separately by controller/view tests and native E2E. Actual OS activation here uses the production adapter through the probe, not a claimed recorded GUI wizard.

`pnpm desktop:check`, focused race tests, bilingual setup views, repository/i18n checks and native-window E2E passed. The native engine/AppKit report in this run contains 34 passing cases, distinct from actual installed-host dispatch above. The package passed Developer ID, provisioning, notarization and Gatekeeper checks. Reinstallation retains this account's earlier authorization: clean-account first Allow/denial, physical Intel and Windows TSF remain unverified. No permission database was reset to simulate first consent.
