# ADR 017: Shared offline Pinyin keyboard with native input-method hosts

Status: Accepted. Shared-core integration and Windows host implementation are in progress. Earlier macOS isolated tests remain historical evidence; fresh cross-platform native and installed-source acceptance is required.

## Shared implementation extension

The Windows implementation reuses the actual keyboard core rather than copying the macOS engine wrapper. `apps/desktop/ime/shared` owns Rime sessions, candidate snapshots, strict UTF-8/UTF-16 boundaries, key policy, Shift tap state, configurable candidate pages and expanded rows, display-to-engine candidate indices, ranking and encrypted database transactions. macOS keeps IMK/AppKit and Keychain/CryptoKit adapters; Windows supplies TSF/native windows and a current-user DPAPI provider. Both stage the same reviewed schema and dictionary sources from `shared/keyboard-data` with the same pinned engine version. Each platform compiles its own native binaries.

Windows builds the pinned Rime sources and dependencies using one C++ ABI. Its private encrypted database adapter requires exported `rime::Db` metadata, methods and virtual table; the official prebuilt Windows library did not provide the required complete ABI. The reviewed source patch and compiler provenance are recorded in the Windows runtime manifest. The unique `ArionRime.dll` dependency belongs beside `ArionKeyboard.dll`; the TSF host loads the verified absolute module path instead of relying on another editor's DLL search path or an unrelated Rime installation.

The shared transaction codec retains the existing macOS encrypted snapshot contents and Keychain policy. Windows uses its own authenticated DPAPI envelope, without plaintext fallback. Ranking uses one Unicode 17 grapheme implementation and preserves the existing trailing-character context policy. The independently encoded legacy-format fixture, official Unicode corpus and native encrypted-storage tests are recorded in [the learning corpus](../../benchmarks/corpora/ime-learning-v1/README.md).

`node scripts/test-shared-pinyin.mjs` checks ownership, malformed Unicode, commit consumption and menu/key policy boundaries. `node scripts/test-windows-pinyin.mjs` runs actual pinned Rime and the production encrypted provider, including full/abbreviated Pinyin, apostrophes, v spelling, partial selection, editing, paging, configured menus, independent sessions and direct punctuation. These gates do not establish installed TSF editor dispatch. Both installed Windows acceptance and a fresh macOS native regression run of the shared implementation remain required.

## Context

The user's complete IMK typing alignment request expands the earlier voice-only IME boundary. Retained Doubao and Chatterfly evidence establishes separate local Pinyin engines, incremental composition, paged candidates, partial selection, editing and learning. Their proprietary code/data are evidence, not implementation dependencies ([alignment](../research/imk-typing-alignment.md)).

## Decision

- Add offline Simplified Chinese full-Pinyin typing to the native Objective-C InputMethodKit host, preserving MyGo and the existing voice coordinator. It must type without the menu-bar app running or a network connection.
- Use pinned official librime 1.17.0 through its versioned C API, one process-wide runtime and independent sessions per controller activation. Universal native packaging remains arm64+x86_64. Bundle a complete prebuilt schema/data closure and licenses; no runtime dependency on Homebrew or schema downloads.
- Use an Arion-owned `arion_pinyin` schema derived from the independently licensed `pinyin_simp` full-Pinyin configuration/dictionary, recording exact source revisions, hashes and transitive licenses. Map direct `ü`/`Ü` key characters to the schema's `v`/`V` spelling without rewriting events passed to the host in English mode or with modifiers. Optional stroke reverse lookup is excluded from this schema; full-Pinyin conversion is retained. This is an initial conversion baseline, not a claim of competitor-level accuracy.
- Chinese mode uses one shared `arion_bilingual` producer (KBD-09/KBD-A13), replacing separate script/English translators and their bounded post-merge filter. Build-time generation merges pinned ESDB level 70 A,B,Z variant 1 with original CSpell technical/company sources, preserving complete eligible word membership and source display case independently of frequency. A versioned sorted TSV and once-built tournament tree replace repeated/truncated prefix aliases and the English Rime schema/table closure. Independent best-first cursors provide complete ranked pagination, exact words first and three-letter completion; prefixes show one preferred spelling per word while exact input exposes case alternatives. The bilingual translator constructs the original Chinese script producer via its generic virtual component API, emits up to three whole-input Chinese words then four English preview candidates, and fairly interleaves the remaining two Chinese / one English entries. It does not drain a giant English stream to find Chinese. Startup validates the index before session creation and reports failure explicitly; Windows reset restores all custom components after registry clearing. Original Chinese Phrase identity, encrypted learning and host ownership remain; English non-Phrase candidates commit through the actual engine and are never learned as Chinese. The generated ranked data retains its CC BY-SA 4.0 frequency-data notice plus complete ESDB/CSpell notices and reproducible source pins. No neural prediction, typo correction or competitor equivalence is claimed.
- The engine owns segmentation, incremental parsing, raw caret, candidate identity/page, partial choices and remaining suffix. The adapter reads actual engine commits separately from displayed preedit. Candidate selection alone never inserts a preview. Convert UTF-8 engine offsets to UTF-16 before native client writes.
- Keyboard and voice composition have separate owners. Starting voice clears pending keyboard composition; physical typing interrupts a voice session before taking keyboard ownership. Late voice messages or disconnects must never clear a newer keyboard range. Deactivation and Escape discard unconfirmed text. Command-modified host shortcuts relinquish composition before pass-through.
- Draw the candidate bar natively in the IMK process (`ime/macos/candidate_panel.m`): one horizontal, non-activating panel below the caret line with bounded pages, number/mouse selection, a next-page chevron and stable revision checks. Its geometry and light/dark themes follow Chatterfly's shipped size presets ([candidate UI research](../research/chatterfly-candidate-ui.md)). The system `IMKCandidates` window was replaced because it renders a vertical, translucent system list. Chrome, shadows and selection are Core Animation layers; only text redraws per key. The window grows but never shrinks while shown, and hiding makes it transparent and click-through, leaving the window list after 2 s idle, because re-ordering a window per word dominated key latency ([results](../../benchmarks/results/imk-context-v1/README.md)). No per-keystroke animation.
- Arion owns the candidate menu (`typing.m`): it reads the engine's candidates by global index, lets the context ranker reorder the first 27, and pages, highlights and selects them itself (Space, 1–9, `-`/`=`, `[`/`]`, Page Up/Down, Up/Down).
- For macOS and Windows Emoji suggestions, a shared native `arion_emoji` Rime filter emits a dedicated non-`Phrase` candidate from a generated exact-word index. The index uses digest-pinned CLDR 48.2 Simplified Chinese names/keywords and fully-qualified Unicode Emoji 15.0 sequences, plus 30 reviewed Arion overrides. Source XML/test data, generator and generated header are checked in for offline regeneration; the package carries their source manifest and Unicode notice. Automatic triggers contain two to six Han characters, exclude skin-tone variants, retain CLDR short names and only closely formed keywords, omit ambiguous keyword-only terms and yield one Emoji per word. The table contains Unicode sequences and IDs, not artwork, fonts or the rime-emoji dictionary. The typed bridge reads candidate type, input range and source association from the same Rime menu as selection. The host ranks only Chinese text candidates and inserts up to two Emoji after the first three text slots; the engine commits the selected Emoji. This avoids shadow-candidate unwrapping into Chinese word learning and keeps mixed Emoji commits out of context learning. The host reads the default-on `emojiSuggestions` switch from app-owned `keyboard.json` on activation. Windows exposes metadata and caret refresh through the validated keyboard-module ABI, applies the same preference to TSF sessions, and excludes Emoji-bearing commits from Chinese context learning. Its candidate window draws typed Emoji with DirectWrite/Direct2D and the installed Segoe UI Emoji font. A bounded cached shaping check admits only one complete cluster and one nonmissing color glyph, so unsupported flags/newer or decomposed sequences do not become selectable rows. No system search dictionary or private Emoji API is used; native and installed-editor acceptance remain distinct gates.
- Caret navigation refreshes Rime's unconfirmed segment when Emoji suggestions are enabled. Rime otherwise retains a menu composed while the caret was mid-input after End returns it to the suffix end; the explicit refresh makes suppression and restoration follow the current caret without replacing the engine's candidate identity.
- The macOS expanded panel retains its largest displayed height until explicitly collapsed or hidden. A partial choice that leaves fewer candidate rows does not shrink the viewport or change its anchored edge; empty space does not introduce selectable candidates.
- The next page opens an expanded grid, as Chatterfly's spread list (`expandedRowCount` 6): `=`, `]`, Page Down, Down or the chevron show up to six pages as rows with aligned columns, the next page as the current (tinted, numbered) row. In the grid, `=`/`]`/Page Down/Down and `-`/`[`/Page Up/Up move between rows (above the first row collapses), Left/Right move within the row, numbers choose in the current row, a click chooses in any row and the up-chevron collapses. Partial selection and subsequent typing or editing keep the grid expanded within the same composition; candidate refreshes restart the page and highlight at the first row. Explicit collapse persists through later edits, and commit, Escape or ownership loss resets the next composition to the single row (KBD-03). Expanding and collapsing animate the bar's layers over 0.3 s and 0.2 s with ease-in-out (Chatterfly's `NSViewAnimation` durations), the rows clipped to the growing bar and fading in. After each change it moves the engine's highlight to Arion's, so keys the engine resolves (punctuation) commit the same candidate. Numbers past a short page select nothing.
- Context ranking (上下文调频, `ranking.m`), in the spirit of Doubao's feature-based candidate sort: after a confirmed Chinese commit, record the pair (last two characters of the previous commit in the same client, committed word) in a separate encrypted snapshot in the learning vault (`arion_context`, written off the key path, bounded to 20,000 pairs, deleted by Reset learned words). While typing, a candidate's score is `1.6·ln(1+count)·0.5^(age/2000) − ln(1+engine rank)`; only candidates as long as the engine's first choice can move, so a prefix never jumps ahead of a whole-input conversion. Context expires after 120 s, on Chinese/English switching, deactivation and keys the host handles; host text is never read. Ranking is always on and has no user setting; a store that fails to open or write disables ranking only, leaving engine order (RNK-03).
- Keyboard preferences (candidates per page 5/6/7/9, size small/medium/large, appearance, highlight color, Emoji suggestions) live in the app's Settings › Keyboard, in the Candidates group. The app writes them atomically to `~/Library/Application Support/Arion/keyboard.json`; the input method reads that file on each activation, and uses the defaults (9, medium, system, yellow, Emoji on) when it is absent. The highlight color is a preset (yellow, orange, red, pink, purple, blue, green, graphite) or, last in the menu, a custom `#rrggbb` chosen with a color well; each option shows a swatch of its fill. Yellow is Sunbeam's `#FFCC00` in both appearances ([ADR 007](007-sunbeam-design-system.md)), blue is Chatterfly's focus box, and the others are macOS's system colors in their light and dark values; a custom color is the same in both. `application.KeyboardPreferences.Highlight` owns the palette and the text rule (white where it holds 3:1 against the fill, else ink `#14110F`), and the app writes the result for each appearance into `keyboard.json` as `highlight.light`/`highlight.dark` (`fill`, `text`), so the input method draws those colors without a palette of its own and falls back to Sunbeam yellow when they are absent. The app also writes the dictation key there as `dictationKey`, which titles the input menu's first item, Voice input (`dictate` over the bridge, disabled while the app is not connected; [IME-06](../../specs/007-ime-ranking.md)). Chinese/English switching is available from the input menu and short standalone Shift release (less than 0.3 s), Shift+Space; switching clears unconfirmed composition before changing mode. The input menu also switches full-width characters and English punctuation in Chinese mode (KBD-07), and Ctrl+. switches punctuation. Both are off by default; the input method owns them in `keyboard/options.json` beside its learning data rather than in the app-written `keyboard.json`, so a choice made without the app survives the app's next settings save. English mode keeps both off in the engine, because Rime's shape post-processor would otherwise widen keys `ascii_mode` passes through.
- Preserve Rime's learning transactions through a custom encrypted user-database backend. Store values in memory and persist only authenticated encrypted snapshots with a separate this-device Keychain key. Do not use stock plaintext userdb, text backups or sync exports. Key/tag/storage errors are explicit; they must not select a plaintext backend or replace an existing vault with a new key. Reset/delete and encrypted backup behavior require independent tests. This extends [ADR 005](005-local-encryption.md), not the account-sync protocol.

## Consequences and gates

Keyboard conversion is a new local candidate producer, not ASR n-best and not a deployed Laya ranker. Full-Pinyin typing, candidate handling, encrypted learning and actual native IMK behavior must all pass [007](../../specs/007-ime-ranking.md) acceptance. The initial lexicon's quality and latency must be measured with original fixtures and real outputs; successful sample conversions do not prove parity. Windows TSF, additional keyboard schemes, cloud candidates and proprietary model equivalence remain separate work.

The encrypted backend uses pinned engine-private C++ interfaces because the public C API does not provide a user-database storage hook. Retain exact header/dependency provenance and ABI checks; upgrade the runtime and adapter together. Native arm64 and translated x86_64 runs each pass 23 actual-engine/AppKit regression cases with synthetic learning keys; x86_64 used Rosetta 2 on arm64, not physical Intel. This verifies the isolated engine/text-system boundary; it does not establish installed IMK dispatch, external-editor behavior or OS-kept-key protection policy. Both ad hoc and Developer ID signed probes on macOS 26.6.2 fail source selection. In the signed run, enable returns `0` but leaves the parent disabled; select returns `-50` despite notarization/Gatekeeper acceptance. Signing is therefore not a demonstrated fix; the TIS state cause and system typing acceptance remain open ([evidence](../research/imk-typing-alignment.md)).

The pre-fix owned-key lifecycle probe verified actual Keychain provisioning, fresh-process learned ranking, exact-owned-key deletion and fail-closed startup with unchanged ciphertext after key loss. It also exposes a policy gap: the previous adapter created a file-based Keychain item; its requested accessibility attribute is absent. This does not establish the required this-device protection. An explicit Data Protection Keychain add with non-synchronizable `AfterFirstUnlockThisDeviceOnly` policy fails with `errSecMissingEntitlement` (`-34018`) under the existing Developer ID signature; the owned namespace is restored absent.

The corrected provider explicitly selects the Data Protection Keychain, verifies accessibility/synchronization attributes, and rejects existing legacy items with a migration-required error before reading secret data. An owned legacy-item test verifies rejection, no new Data Protection item and no vault bytes; cleanup deletes only the owned item. Native synthetic storage and policy checks pass. No implicit migration or file-based fallback is permitted. Apple's [TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains) requires provisioning-profile authorization for the entitlement-derived Data Protection access groups. The macOS application identifier supplies the default group ([access groups](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps)). A matching Developer ID provisioning profile is now available and validated against the existing signing certificate. The profile-bearing signed harness passes real provisioning, fresh-process learned ranking, exact-owned-key deletion, fail-closed key-loss startup and cleanup. Returned attributes verify `AfterFirstUnlockThisDeviceOnly` and nonsynchronizable policy; the persistent reference resolves in the Data Protection store and is absent from the legacy store. Both stores and the owned profile are restored absent. This verifies the OS-kept policy/lifecycle on the recorded Mac, not physical device migration or backup behavior. Actual installed IMK dispatch remains a separate gate.

## Keyboard interaction feedback

Standalone left/right Shift toggles on release within 0.3 s. Any intervening key/modifier, overlapping Shift keys, cancellation or deactivation invalidates the tap; Shift+Space remains compatible and cannot toggle again on release. IMK explicitly requests key-down and modifier-change events. Mode switches retain the existing discard policy for unconfirmed typing.

A separate nonactivating, click-through native badge shows the selected mode beside the host caret for 1 s, using the candidate appearance preference and localized catalog labels. The window appears and disappears immediately; inside it, the previous mode's label folds away around the horizontal axis and the new one unfolds (Core Animation, 0.12 s per half, skipped under Reduce Motion), so each switch reads as 中 turning over to 英 or back. It stays within the caret screen, flips above the line near the bottom edge, and disappears on typing, voice takeover or focus loss. Rapid switches replace its dismissal timer. No valid caret means no badge.

The Arion schema replaces the inherited multi-choice punctuation arrays with direct common-symbol mappings and disables slash-code symbol recognition. Quotes retain paired output; apostrophe syllable boundaries and candidate paging retain their existing behavior. These changes use Rime's configured engine commit path rather than inserting candidate display text.
