# ADR 025: Windows local polishing

## Status

Accepted by the user's request to implement Windows local polishing. Extends [ADR 018](018-staged-gguf-rewriting.md) to Windows x64 with the same model bytes and shared staged recipe.

## Decision

- Keep the existing catalog ID for installed-model compatibility. Add Windows x64 to the same pinned Qwen3.5-2B Q4_K_M artifact; use a platform-neutral display name. Provisioning still requires an explicit Download action, validates the complete size and SHA-256, and keeps weights outside the application.
- Build llama.cpp b11734 from its digest-pinned source archive. Windows ships two statically linked CPU executables: the x64 baseline and an AVX2/FMA/F16C/BMI2 build. The worker chooses the accelerated executable only after CPUID confirms every compiled instruction requirement and OSXSAVE, and XGETBV confirms XMM/YMM state preservation. Disable OpenMP and link compiler runtimes statically. Packaging validates both executables' DLL imports and launches the baseline with only the Windows system directory on PATH. The upstream Windows binary archive omits its Visual C++ runtime dependencies; a trial MinGW build with shared libraries and static compiler runtimes hung on exit and was rejected.
- Use Windows AF_UNIX stream sockets. Create the temporary socket directory with a protected current-user DACL inherited by its children; POSIX mode bits alone do not establish a Windows access boundary. Resolve its short filesystem name to accommodate Windows TEMP paths within the Unix-socket address limit. There is no TCP listener or remote inference route.
- Hide both console workers. A noninheritable kill-on-close Windows Job Object owns each pipe worker and its descendants. The pipe worker waits for the load request before it can start its native child, so job assignment finishes before descendant creation. Closing the client or losing its process reaps that job. Native subprocess startup failures fail explicitly.
- Use one CPU slot, four default decoding threads and the existing 4096-token context. Windows uses 512-token batches/microbatches and up to eight prefill threads by default, scaled to half the logical CPU count; an explicit higher decoding thread count remains the prefill minimum. Windows CPU final requests have a thirty-second deadline; the macOS default stays ten seconds and cloud stays fifteen. The earlier ten-second Windows probes timed out on cold prompts and are preserved. Ordinary slot erasure has a six-second Windows bound. No GPU acceleration or minimum-hardware qualification is implied.
- Windows cancellation terminates the native child immediately. HTTP disconnect and slot erase alone can race a native task not yet enqueued, allowing cancelled KV state to survive. The next explicit rewrite loads the same pinned model within its request budget; cancelled content is never retried. Reload itself observes cancellation, including while waiting for an unready health endpoint. A failed reload makes the pipe worker exit after reporting failure.
- Preserve native template token-budget checks, thinking-disabled generation, private runtime working directory, session slot erasure, no disk prompt cache, source ownership and cancellation behavior. Enabled polishing becomes ready only after the installed model and native runtime load successfully.

## Verification

The opt-in `TestNativeWindowsLifecycle` runs authored Chinese, English, list and context-backed spelling cases through the actual pipe worker with the product deadline, records per-case output and timings, and checks cancellation, retry and close. Windows unit tests inspect the directory's returned security descriptor and terminate a real child through job ownership. [Windows reproduction](../../benchmarks/reproduction/windows-local-rewrite-v1/README.md) retains the measured runtime identity, failures and final observations; these are integration probes, not held-out model-quality or acoustic-recognition evidence.

The [installed-runtime repeat](../../benchmarks/reproduction/windows-installed-local-rewrite-v1/README.md) passes the same lifecycle test using the actual installed executables and application-downloaded model, including the final cancellation-aware reload. Installed binary hashes match canonical staging and the installed model matches its pinned catalog identity. GUI checks and background application activity were ongoing, so this repeat establishes installed-artifact lifecycle behavior rather than an isolated latency benchmark or native editor delivery.
