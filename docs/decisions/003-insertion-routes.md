# ADR 003: Shortcut-mode insertion routes

Status: Accepted. macOS and Windows external delivery insert at the caret focused at commit time.

## Context

DSK-06 requires one commit at the caret focused at commit time. A caret move, a switch to another editable field, or an edit in the captured field still inserts there. External delivery posts system paste without an editable-focus gate. A secure field is refused. On Windows, a focused standard edit or rich edit with ES_READONLY is not pasted; the text stays on the clipboard. AX selected-text writability does not prove that a web renderer implements insertion. Field ancestry, application names and framework names cannot establish a reliable universal editing transport. The [competitor investigation](../research/competitor-text-insertion.md) distinguishes an owned IMK client from external application delivery; its static findings are evidence, not external-app acceptance.

## Decision

macOS system-IME mode commits through its existing owned IMK client. macOS global-shortcut mode uses one guarded system-paste transaction for every external target. Global dictation and translation shortcuts always select external delivery, including with Arion selected as the input source ([ADR 033](033-voice-shortcut-delivery.md)). Other entry points select their route at session start from the current input source; Settings exposes neither mode nor transport choices. There is no AX write, Unicode-event route, application allowlist, ancestor-based route selection, probing write or automatic second transport. AX remains available for target capture, focus/selection validation and consent-gated reading.

A captured opaque target belongs to one session/generation and is consumed by one matching commit. A stale identity cannot consume another session's target. Commit carries the session's cancellation context. At commit the adapter reads the focused field. The same editable field keeps the paste and uses its current selected range, so a caret move or an edit there still inserts. Another editable, non-secure field receives that one paste instead. A secure field is refused and is not copied to the clipboard. External delivery posts one system paste, Command-V on macOS and Ctrl-V on Windows, into the frontmost application other than Arion. That post does not require the focused element to be classified as an editor. The text is left on the clipboard, without restoring the previous contents, when Arion itself is frontmost, when the frontmost application cannot be read, on Windows when the focused control is a standard edit or rich edit with ES_READONLY, or when Windows does not accept the Ctrl+V injection. A rejected injection is not a posted paste. That style check is not an editable-focus classification. This applies equally to polishing and translation. A failed re-read of the selected range is not a destination change. A range that is successfully read and differs still is. Windows UI Automation still classifies editors for context and for the positive no-input fact: a value that is not read-only, a text pattern that is not read-only, TextEditPattern, or a caret range that is not read-only. That classification does not choose paste versus copy. The shared rule is `infrastructure/focusclass`. Missing focus at session start does not prevent recognition or processing; an editable field focused by commit time receives the result normally. An empty editable field is a valid destination. The paste transaction then checks cancellation, that destination's focus and selection, secure input, and clipboard ownership before posting. The final native post repeats those checks. A destination change found before posting does not retry the paste; the text is left on the clipboard. OS focus/clipboard APIs provide no atomic validation-and-write primitive; these checks reduce races without claiming to eliminate them.

Transactions serialize access to the system clipboard across target-provider instances. Each owns its snapshot of every readable item and data type, text, unique ownership marker and preallocated Command-V events. On macOS the snapshot skips a type whose name is not a valid UTI or whose data cannot be read, such as Qt rich-text flavors from WeChat and QQ, and skips an item left with no readable type; restoration writes each saved item separately so one rejected item does not discard the others, and still reports the failure. Snapshot/read or staging errors stop before posting; a clipboard with content but no readable type is a snapshot failure. A changed clipboard before posting stops the attempt. Cleanup restores the snapshot only while its change count and marker still belong to Arion; another application's newer clipboard is preserved. Snapshot failures and restoration failures have explicit typed errors. The transaction phase is prepared, staged, posted, restored, restore-failed, left, or copied. restore-failed sets `CLIPBOARD_RESTORE_FAILED` on an already posted uncertain outcome and is not a clean paste. left means another owner has the clipboard and is left unchanged. The 400 ms hold and the macOS snapshot's skip of invalid UTIs are unchanged. Clipboard contents and target text are never diagnostics.

Command-V is posted once. On Windows the post is Left Ctrl+V with scan codes. Shift, Alt and the Windows key that are already down are released first, because SendInput does not clear them and they turn the chord into a literal V or no paste. V is posted while Left Ctrl is still down; Left Ctrl is released in a following call. The hold hook ignores those injected events, so the release is not a press or release of the dictation key. A 400 ms hold then gives the target time to consume the board; this interval is not an acknowledgement and cannot guarantee arbitrarily delayed consumption. Cancellation after posting cannot undo delivery or shorten clipboard retention; cleanup still runs once. No fallback or retry follows a posted/uncertain result. Unicode input and WM_PASTE are not that fallback when a hook discards the chord or the target reads the clipboard after the hold. Text is preserved exactly, including Unicode and line breaks; Arion does not synthesize Return. Hosts can apply their own paste policies, so terminal and rich-editor compatibility still needs actual host testing.

## Commit outcome

A posted paste returns `unknown` and is labeled "Pasted", never inferred `applied` from a length increase or matching substring. `CLIPBOARD_RESTORE_FAILED` preserves that uncertain outcome and displays a warning to check the editor before retrying. A pre-post rejection other than a moved destination returns `not_applied` with an explicit reason; text remains available for user-controlled copying. Outcome `copied` means the text was left on the system clipboard; the pill says "Copied". That is Arion being frontmost, an unreadable frontmost application, a Windows read-only standard edit or rich edit, or a Windows Ctrl+V injection SendInput did not accept. A posted paste is labeled "Pasted" on every platform, including Windows automatic delivery. A cancelled session cannot publish a late completion or start edit learning. Windows posts the same single paste. Its clipboard restore keeps the previous Unicode text, or clears the board when it was empty, while preserving a newer clipboard owner. A posted paste whose history exclusion cannot be set restores the previous text and fails. Old persisted delivery values remain compatible and do not select a different transport.

## Root-cause evidence

In Chromium `147.0.7727.149` (matching the inspected Lark framework's version), [`setAccessibilitySelectedText:`](https://github.com/chromium/chromium/blob/147.0.7727.149/ui/accessibility/platform/ax_platform_node_cocoa.mm#L3463) dispatches `kReplaceSelectedText` and discards the action's boolean result. The web node's [`BrowserAccessibility::AccessibilityPerformAction`](https://github.com/chromium/chromium/blob/147.0.7727.149/ui/accessibility/platform/browser_accessibility.cc#L1284) implements `kSetValue` but not `kReplaceSelectedText`; its default returns false. The renderer also lists replacement as an [unreachable action](https://github.com/chromium/chromium/blob/147.0.7727.149/content/renderer/accessibility/render_accessibility_impl.cc#L400). This explains why replacing the whole AX value and inserting through selected text have different behavior. These are upstream sources, not proof that a vendor's binary is unmodified.

Lark's inspected chat editor is under `AXWebArea`. A temporary Computer Use AX value-write draft was cleared without sending; it does not exercise Arion's selected-text or Unicode commit. Historical diagnostics omit target identity and route, so an `unknown` outcome cannot be attributed to Lark or to a particular API. App/framework classification tests alone do not reproduce an insertion failure.

Editable-focus false negatives are a separate defect from that transport limit. Current Chromium maps a multiline contenteditable root to `AXTextArea` and marks `AXSelectedTextRange` writable when the node is editable, while `AXValue` and `AXSelectedText` are often not writable. The same root exposes `AXEditableAncestor`. Inner paragraphs and text runs are `AXGroup` or `AXStaticText` with that ancestor, not `AXTextField`. On Windows the same composer is often a Group, and the caret's text range is not read-only even when the page Document's text pattern is. Reading only the focused node's own attributes classifies those composers as empty focus. External delivery on both platforms no longer uses that classification to choose the clipboard. There is no per-app exception. A canvas or custom control that exposes none of these signals still cannot be classified; the missing signal is an editable ancestor, a writable value or selected-text attribute, TextEditPattern, or a caret range that is not read-only.

## Verification

Isolated adapter tests cover cancellation at transaction boundaries, serialization/queue cancellation, clipboard failures, unknown outcomes and identity/duplicate rejection. Native transaction tests use real named pasteboards and real CGEvent construction, intercepting delivery: multi-item/binary restoration, empty originals, ownership changes, a destination change before posting (no retry; text left on the clipboard), secure fields (refused and not copied) and one post. They do not assert that a caret move or field switch before commit is rejected. They do not establish external-editor delivery.

`TestGuardedSystemPaste` runs the production adapter against a separate owned AppKit/WebKit application with actual Command-V dispatch and editor input observations. It covers exact mixed Unicode/multiline selection replacement, duplicate commit, insertion into a newly focused editor, insertion at a moved caret, insertion into an empty editor, missing editable focus both before and after capture, a selection in a read-only transcript, cancellation, stale identity, secure fields and clipboard restoration. Clipboard-only cases require the exact processed text to remain available and both editors to stay unchanged. The clipboard check compares text as well as ownership, so retaining an earlier test value cannot pass it. See [E2E](../quality/e2e.md) for the opt-in command and evidence limits. An installed Chrome is also tested with an isolated temporary profile and local textarea/contenteditable fixtures. Actual Lark, Codex, office and terminal acceptance remains separate.

The former input-mode selector and delivery controls are removed. Global shortcuts use external-editor delivery. For other entry points, the current Arion input source selects IMK for a new session; other sources select external-editor delivery. This choice is fixed for the session, with no automatic retry through another route after failure. Legacy stored input modes are retired; internal transport preferences remain readable for compatibility.
